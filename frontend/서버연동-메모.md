# 서버 연동 메모 — 프론트 담당에게

서버(`backend/`)가 먼저 만들어졌고 **앱(`frontend/`)은 아직 안 바뀐** 일을 모은다.
앱을 고치는 사람(또는 AI)은 작업 전에 이 파일을 읽고, 끝낸 항목은 [x]로 바꾸고 날짜 · 한 줄 메모를 남긴다.
서버 계약의 기준은 `docs/api/습관몬스터_API명세_v5.md`. 서버 오류는 `{code, message, errors?}`이고 `message`는 화면에 그대로 띄워도 된다.

## 1. 습관 추가 · 연장 · 그만두기 (4-1, 서버 완료 2026-10-23)

- 기획서: `docs/기획/2026-10-21-습관-기간-연장.md` (사용 흐름 · 화면 · 예외)
- 서버 테스트: `backend/server/src/test/java/kr/habitmonster/habit/HabitApiTest.java`
- 결정: 결정-기록 D-47 (기간 완료도 칸을 차지 · 최소 1개)

### 규칙 요약
- 습관 상태 `ACTIVE`(진행 중) · `ENDED`(기간 완료, 연장 · 그만두기 대기) · `STOPPED`(그만둠, `GET /habits` 기본 목록에서 빠짐).
- **칸 = 진행 중 + 기간 완료**. 최대 5개(`HABIT_LIMIT`), 최소 1개(`LAST_HABIT`). 연장은 칸 수가 그대로라 상한 검사가 없다.
- 시작일: 오늘 체크인을 아직 안 냈으면 오늘, 이미 냈으면 내일 (`startDate`로 내려온다).
- 기간 완료 습관은 체크인 대상이 아니다 (챗봇이 묻지 않음). 연장하면 다시 대상.

### API
| 요청 | 성공 | 실패 |
| --- | --- | --- |
| `POST /habits` (중복 방지 키 필수) `{categoryCode, measureTypeId, name, dailyTarget, periodCode}` | 201, `GET /habits`의 한 줄과 같은 모양 | 400 값 형식 (`errors[].field`), 422 `CATEGORY_LOCKED` · `HABIT_LIMIT` |
| `POST /habits/{id}/renew` (중복 방지 키 필수) `{periodCode, dailyTarget?}` — `dailyTarget` 생략 = 이전 값 | 200, 같은 모양 (`status: ACTIVE`, `filledDays: 0`) | 404 남의 · 없는 습관, 400, 409 `HABIT_NOT_ENDED` |
| `POST /habits/{id}/stop` (키 없음) | 200 `{habitId, status: "STOPPED"}` | 404, 409 `HABIT_ALREADY_STOPPED`, 422 `LAST_HABIT` |

`GET /habits` 한 줄: `{habitId, categoryCode, name, measureTypeId, unit, dailyTarget, periodCode, startDate, filledDays, periodDays, status}`
`GET /me/status`에 `endedHabitCount`(기간 완료 습관 수)가 이미 있다.

### 앱에서 할 일
- [ ] **추가 · 그만두기를 서버로**: `HttpGameRepository.addHabit` · `removeHabit`가 지금은 `_local`(앱 안)만 바꿔서 다시 켜면 사라진다.
  `POST /habits` · `/habits/{id}/stop`을 부르고 응답으로 `GameState`를 고친다 (3-5의 `applyPurchase` 같은 `apply*` 패턴).
  `LAST_HABIT`은 지금 문구("습관은 1개 이상 있어야 해요")와 같다. 앱의 미리 검사 `canRemoveHabit` · `canAddHabit`도 "진행 중 + 기간 완료" 기준으로.
- [ ] **`Habit` 모델에 상태 · 채운 날 · 채울 날**: `status` · `filledDays` · `periodDays`. `HttpGameRepository._habit`에서 채운다.
  시연 모드(`LocalGameRepository`)는 기간 진행이 없으니 기본값(진행 중, 0 / 기간)으로 두고 칩을 숨긴다.
- [ ] **연장 (새 메서드 `GameRepository.renewHabit(Habit, periodIndex, target?)`)**: 서버는 `POST /habits/{id}/renew`, 시연 모드는 기간 완료가 생기지 않으니 아무것도 안 해도 된다.
- [ ] **"내 습관" 화면 (`features/home/habit_manage_screen.dart`)** — 기획서 4장
  - 진행 중 카드에 칩 "4 / 30일 채움"
  - 기간 완료 카드: 금색 테두리 · "기간 완료!" 띠 · 칩 "30 / 30일 채움" · [연장하기] · [그만두기]
  - 연장 창(`PopupCard`): 기간 7 · 30 · 100일 버튼 + 하루 목표 조절(O/X 습관은 없음) + [연장하기] · [취소]
  - 연장 뒤 알림: "다시 시작! 오늘부터 체크해요" / 오늘 체크인을 냈으면 "내일부터 체크해요"
  - 5칸이 꽉 찼고 기간 완료가 있으면 안내에 "기간 완료 습관을 연장하거나 그만두면 자리가 생겨요"
- [ ] **홈 "습관" 아이콘 알림 점**: `endedHabitCount > 0`이면 표시 (`home_screen.dart`의 `_IconSpot(badge: …)`).
- [ ] 테스트: `test/http_game_repository_test.dart`에 추가 · 연장 · 그만두기 묶음 (MockClient), 화면 캡처 390 · 360폭.

## 2. 목표 등록 · 수정 · 삭제 · 완료 (4-2, 서버 + 앱 완료 2026-10-28) — 알림용

- 기획서: `docs/기획/2026-10-23-목표-서버-유료칸.md` · 결정 D-48

기획서 `docs/기획/2026-11-08-AI대사-알림.md` · 결정 D-64. **앱 쪽은 프론트 담당** (사용자 11-09).

### 5-1. 체크인 대사 `POST /checkins/today/dialogue` (본문 없음)
```json
// 200
{ "revision": 1, "line": "30분이나 뛰었구나, 멋져!", "source": "LLM" }   // source: LLM | TEMPLATE
```
- 제출(`POST /checkins/today`) · 다시 체크(`PUT`) 응답을 받은 **뒤에** 부른다. 대사는 보상과 상관없다 — 실패해도 결과 화면은 그대로.
- 같은 revision이면 서버가 저장된 대사를 그대로 준다 → 다시 불러도 괜찮다 (중복 방지 키 필요 없음).
- 오늘 제출 전이면 409 `CHECKIN_REQUIRED`. 서버가 3초 안에 못 만들면 스스로 템플릿 대사를 준다 (최대 3초 남짓 걸릴 수 있음 → 말풍선 "…").
