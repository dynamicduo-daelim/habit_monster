# 습관 몬스터 앱 — AI 시스템 정리 (부속 문서 v1)

> **이 문서의 위치**: `습관몬스터-기획정리-v1.md`(기획 합의 문서)의 부속 문서. 본문 5-2에 언급된 "AI 자유대화 보정"과, 별도로 논의된 "개인화 기억 시스템"을 함께 정리한다.
> 상태 표시는 본문과 동일한 규칙을 따름 — `[확정]` / `[미결정]` / `[추후검증]`(방향은 정했으나 구체 수치·플랫폼은 검증 필요).

## 0. 핵심 원칙 — 두 시스템은 반드시 분리한다

- `[확정]` 이 앱에는 AI를 쓰는 **서로 다른 목적의 두 시스템**이 존재하며, 이름이 비슷해 보여도(둘 다 "자유 텍스트 → AI 판정") **로직·프롬프트·저장소·판정 결과를 절대 공유하지 않는다.**
- `[확정]` 이유는 기술이 아니라 **신뢰(trust) 문제**다: 하나는 "사용자를 의심하는 AI"(경제 판정), 하나는 "사용자를 걱정하는 AI"(관계 형성)다. 둘이 조금이라도 얽히면, 사용자가 감정적으로 털어놓은 이야기가 경험치 계산에 영향을 줄 수 있다는 의심을 갖게 되고, 이는 이 기능을 만든 원래 목적(이탈 방지)과 정반대로 작동한다.
- `[확정]` 공유 가능한 것은 **인프라뿐**이다 (아래 3장 참고). 둘 다 같은 로컬 모델 서버에 서로 다른 요청을 보내는 것은 문제없다.

## 1. 시스템 A — AI 자유대화 보정 (기존 5-2, 경제 판정용)

| 항목 | 내용 |
|---|---|
| 목적 | 체크인 수치 조작 방지용 **이상치 감지** — 숫자는 정상인데 실제로는 안 한 것 같은 신호 포착 |
| 트리거 위치 | 체크인 플로우 내부 (수행 기록과 함께 발생) |
| 입력 | 그날 습관 수행에 대한 짧은 코멘트 |
| 판정 범위 | 좁은 이진 판단 (미수행 신호인가 아닌가) |
| 출력 | 숫자 보정치 — **±20% 이내 하향 보정만** |
| 경제 시스템 영향 | **있음** — 경험치 계산에 직접 반영됨 |
| 데이터 보존 | 장기 저장 불필요, 판정 즉시 소비되는 일회성 신호 |
| 역할 한계 | `[확정]` "성실함을 판단"하는 무거운 역할은 지지 않음 — 어디까지나 **보정 신호**일 뿐, 주 판정 기준은 기존 정량/자가진단 공식 |

## 2. 시스템 B — 개인화 기억 시스템 (신규, 관계/이탈방지용)

### 2-1. 목적 및 원칙

- `[확정]` 목적: 몬스터가 사용자의 개인적인 이야기를 기억하고 다음 대화에서 자연스럽게 언급함으로써 **정서적 애착 → 중도 이탈 방지**.
- `[확정]` 경제 시스템(레벨/경험치)과 **완전히 무관**하게 동작한다.
- `[확정]` 대화를 계속 이어가게 만드는 것이 목적이 아니라, **가끔** 안부를 묻고 기억해주는 정도로 제한한다 (과도한 챗봇화 지양).

### 2-2. 아키텍처 — 5개 레이어

```
[트리거] → [추출] → [저장/매칭] → [후속질문 생성] → [모델 서빙]
```

#### ① 트리거 레이어 — AI 불필요
- `[확정]` 마지막 대화 후 N일 경과 등 **규칙 기반**. AI가 들어갈 필요 없음.

#### ② 추출 레이어 — 자유 텍스트 → 구조화된 fact
- `[확정]` 사용자의 답변("요즘 감기로 힘들었어")을 자유 생성이 아니라 **스키마를 강제하는 구조화 출력**으로 처리한다.
- `[추후검증]` vLLM(xgrammar/guidance 백엔드), Ollama(OpenAI 호환 JSON 스키마 모드) 모두 2026년 기준 로컬 모델에서 JSON 스키마 강제 출력을 지원 — 파싱 실패 리스크를 프롬프트 튜닝이 아니라 디코딩 단계에서 차단 가능.
- `[확정]` 프롬프트 입력 = 사용자의 새 답변 + **그 사용자의 기존 활성 fact 목록**.
- 출력 스키마 예시 (설계 참고용, 실제 구현 아님):
  ```json
  {
    "new_facts": [{"text": "최근 감기로 아팠음", "topic": "health"}],
    "updates": [{"fact_id": "...", "resolved": true}],
    "no_relevant_content": false
  }
  ```

#### ③ 저장/매칭 레이어
- `[확정]` **벡터DB/임베딩 검색 불필요** — 사용자 1인당 활성 fact 수가 많아야 수십 개 수준이라, 기존 fact 전체를 그대로 프롬프트 컨텍스트에 넣고 모델이 매칭 여부를 판단하게 하면 충분.
- `[확정]` 단순 관계형 테이블 하나로 충분:
  ```
  user_facts(id, user_id, text, status[active/resolved/stale], created_at, updated_at, last_referenced_at)
  ```
- `[미결정]` `stale` 전환 기준일(예: 2주 미해결 시 자동 만료) — 본문 5-4의 "60일 미접속 동결" 로직과 같은 패턴으로 재사용 가능하나 구체 일수는 미정.

#### ④ 후속 질문 생성
- `[확정]` 완전 자유생성보다 **템플릿 + 슬롯필링** 권장 (예: "{fact} 괜찮아?"). 로컬 소형 모델의 어색한 문장 생성 리스크를 줄이기 위함.

#### ⑤ 모델 서빙
- `[확정]` "API를 쓰지 않는 로컬 AI" 요건 충족 = 상용 API(OpenAI/Claude 등) 대신 **자체 운영 서버에서 오픈소스 모델을 서빙**하는 방식.
- `[추후검증]` 개발/프로토타이핑: **Ollama** (설치·운영이 가볍고 로컬에서 OpenAI 호환 API 바로 사용 가능).
- `[추후검증]` 배포까지 고려 시: **vLLM + 서버리스 GPU**로 서빙 레이어만 교체. 비즈니스 로직이 OpenAI 호환 HTTP 엔드포인트만 바라보게 설계하면 로직 변경 없이 서빙만 교체 가능.
- `[추후검증]` 모델 크기: 8~9B급 양자화 모델(Qwen3-8B, Llama-3.1-8B-Instruct, GLM-Z1-9B 등 후보)로 충분 — 이 태스크는 대형 모델이 필요한 수준의 추론이 아님.
- `[확정]` **트레이드오프 인지**: 로컬 소형 모델은 상용 대형 모델보다 미묘한 뉘앙스 판단(예: "부분 해결" vs "완전 해결") 정확도가 낮을 수 있음 — API 미사용 선택에 따른 실질적 비용.

### 2-3. 배포 인프라 참고 수치 (2026년 기준, 변동 가능성 있으니 재검증 필요)

| 항목 | 내용 |
|---|---|
| 상시 GPU 임대 | 시간당 $4~10 수준 — 개인 사이드 프로젝트엔 부적합 |
| 서버리스 GPU (Modal) | A10G 기준 초당 약 $0.0005 |
| 서버리스 GPU (RunPod) | 초당 약 $0.0003 (가장 저렴한 축) |
| 서버리스 GPU (Replicate) | 초당 약 $0.001, 사전 구축 모델 위주 |
| 손익분기 기준 | 하루 요청 약 4.7만 건 미만이면 서버리스가 상시 임대보다 저렴 → 개인 습관 앱은 이 기준에 한참 못 미침 |
| vLLM 콜드 스타트 | 서버리스 위 스냅샷 방식 기준, 초기 3~5회 콜드 호출 후 안정화되기까지 최대 약 70초 소요 가능 |
| 콜드 스타트 대응 | 실시간 채팅이 아니라 "체크인 후 잠시 뒤 메시지" 구조이므로 **비동기 생성 + 푸시 알림**으로 설계하면 문제되지 않음 |

### 2-4. 안전/설계 책임 — 선택 사항 아님

- `[확정]` "힘든 일 없어?"라는 질문은 사용자가 정말 심각한 내용(자해/위기 신호 등)을 털어놓을 가능성을 내포한다. 이 경우 게임화된 톤으로 가볍게 후속 질문하는 것은 부적절할 수 있다.
- `[미결정]` 답변에서 위기 신호가 감지될 경우의 처리 방식(게임화 로직을 타지 않고 중립적으로만 저장/처리 등) — 방향은 필요하다는 데 합의되었으나 구체 설계는 미정.
- `[확정]` 이 fact 테이블은 다른 게임 데이터(레벨, 아이템 등)보다 **접근·노출을 보수적으로** 다뤄야 한다.
