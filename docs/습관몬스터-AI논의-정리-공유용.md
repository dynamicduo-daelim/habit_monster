# 습관 몬스터 앱 — AI 관련 논의 정리 (팀 공유용)

## 1. 기술 스택 개요

### 백엔드

- Spring Boot + JWT
- RDB(PostgreSQL/MySQL) — 종(species) 마스터 테이블 + 유저별 개체 인스턴스 테이블 구조 (이커머스 상품-옵션 모델링과 유사한 패턴)
- 스케줄러(Spring `@Scheduled`/Spring Batch) — 미접속 동결, 기간 배수 보너스 등 배치성 로직
- Redis — 도감 진행률 등 자주 조회되는 값 캐싱
- **MSA/Kafka·RabbitMQ는 이 프로젝트 규모(2인, 개인용 앱)엔 오버엔지니어링으로 판단** — 모듈러 모놀리스로 시작하는 것을 권장

### 프론트엔드

- Flutter + Riverpod
- FCM 푸시 알림(체크인 리마인더)
- 오프라인 체크인 → 재연결 시 동기화

### 이 프로젝트에서 학습 가치가 큰 패턴

- **전략 패턴**: 정량 지표 vs 자가진단, 서로 다른 경험치 공식을 인터페이스로 추상화
- **상태 머신**: 개체 진화 3단계(기본형→1차→최종형)를 명시적 전이로 모델링
- **설정 기반 밸런싱**: "기본치 10" 같은 상수를 코드가 아닌 DB/설정 테이블로 분리해 재배포 없이 튜닝 가능하게
- **중복 제외 랜덤 추첨**: 시드 고정 테스트, 분포 검증
- **멱등성**: `(user_id, habit_id, date)` 유니크 제약으로 하루 1회 체크인 보장

## 2. AI 시스템 검토 과정

### 2-1. vLLM/로컬 AI 현실성 검토

- vLLM의 핵심 강점(동시 다수 요청의 배치 처리)은 개인용 단일 유저 습관 앱에선 거의 활용되지 않음.
- 모델 크기는 8~9B급 양자화 모델(Qwen3-8B, Llama-3.1-8B-Instruct, GLM-Z1-9B 등)로 충분.
- 상시 GPU 임대는 비용 부담이 크고(시간당 $4~10), **서버리스 GPU**(Modal, RunPod 등, 초당 $0.0003~0.001 수준)가 요청이 드문 개인 앱에 적합.
- vLLM을 서버리스 위에 올릴 경우 **콜드 스타트**가 안정화 전까지 최대 약 70초 걸릴 수 있으나, 이 기능은 실시간 채팅이 아니라 "체크인 후 잠시 뒤 메시지"이므로 **비동기 생성 + 푸시 알림**으로 설계하면 문제되지 않음.

### 2-2. 기존 5-2(AI 자유대화 보정) vs 개인화 기억 시스템 — 별도 시스템 원칙

| 구분             | 5-2 AI 자유대화 보정         | 개인화 기억 시스템            |
| ---------------- | ---------------------------- | ----------------------------- |
| 목적             | 체크인 수치의 부정/허위 감지 | 정서적 유대감 형성(이탈 방지) |
| 경제 시스템 영향 | **있음** (경험치 직접 반영)  | **없음**                      |
| 판정 범위        | 좁은 이진 판단               | 넓은 자유 추출                |

- **분리해야 하는 이유는 기술이 아니라 신뢰 문제**: 사용자가 감정적으로 털어놓은 이야기가 경험치 계산에 영향을 줄 수 있다는 의심이 생기면, 이 기능을 만든 목적(애착 형성)과 정반대로 작동함.
- 공유 가능한 건 인프라(모델 서버)뿐, 프롬프트·출력 스키마·트리거 시점·저장 테이블은 완전 분리.

### 2-3. 개인화 기억 시스템 설계 — 5개 레이어

배경: 각 캐릭터와의 상호작용과 애착 형성이 사용자의 이탈을 줄이는 요소가 될 수 있는지에서 출발.

```
[트리거] → [추출] → [저장/매칭] → [후속질문 생성] → [모델 서빙]
```

1. **트리거**: 규칙 기반(마지막 대화 후 N일 경과). AI 불필요.
2. **추출**: 자유 텍스트 → 구조화 출력(JSON 스키마 강제). vLLM/Ollama 둘 다 지원.
3. **저장/매칭**: **벡터DB/임베딩 불필요** — 유저 1인당 활성 fact가 수십 개 수준이라 기존 fact 목록을 통째로 컨텍스트에 넣고 판단시키면 충분. 단순 관계형 테이블(`user_facts`: id, user_id, text, status[active/resolved/stale], created_at, updated_at)로 처리.
4. **후속 질문 생성**: 완전 자유생성보다 **템플릿 + 슬롯필링** 권장(소형 모델의 어색한 문장 리스크 완화).
5. **모델 서빙**: 개발은 Ollama, 배포까지 고려하면 vLLM+서버리스로 교체 — 비즈니스 로직이 OpenAI 호환 엔드포인트만 바라보게 하면 서빙 레이어 교체가 쉬움.

- **안전 고려사항**: 사용자가 심각한 내용(위기 신호 등)을 털어놓을 가능성이 있으므로, 감지 시 게임화된 후속 질문 로직을 타지 않고 중립적으로 처리하는 안전장치가 필요. 저장 데이터는 다른 게임 데이터보다 보수적으로 취급.

### 2-4. 필요성 재검토

- 개인화 기억 시스템은 습관 측정과 무관한 대화 기능이라, 기획서 0장의 "게임은 습관의 수단" 원칙과 **정체성 이탈 리스크**가 있다는 지적이 있었음.
- 애착 형성 효과는 검증된 전제가 아니라 가설이며, 성공 지표도 아직 정의돼 있지 않음.
- 설계 복잡도(서버리스 배포, 콜드스타트 대응, 서빙 추상화) 중 일부는 **기능 자체의 요구가 아니라 배포 완성도를 보여주기 위한 확장 요소**라는 지적 — "기능 요구"와 "확장 요소"를 문서에서 태그로 구분해둘 것을 제안함.

### 2-5. (개인화 기억 시스템 참고 사항) 캐릭터성 AI / Agent NPC 구조

- "Agent NPC"라는 실제 업계 카테고리가 존재(NVIDIA ACE, PUBG Ally, 인조이 등 상용 사례).
- 어시스턴트 AI와 캐릭터 AI의 차이는 모델 구조가 아니라 **정렬(alignment) 목표의 차이** — 전자는 도움이 되도록, 후자는 캐릭터를 깨지 않도록 학습됨.
- 여러 캐릭터 처리 방식 3단계:
  1. **프롬프트 기반**(가장 흔함): 하나의 공유 모델 + 캐릭터 데이터를 요청마다 주입. 캐릭터는 AI가 아니라 데이터.
  2. **LoRA 어댑터**: 하나의 베이스 모델 + 캐릭터별 경량 어댑터(10~100MB). vLLM은 서로 다른 LoRA 어댑터를 쓰는 요청도 같은 배치에서 동시 처리 가능.
  3. **독립 파인튜닝 모델**: 캐릭터(유형)마다 별도 소형 모델. 학계/로컬-오프라인 지향 연구에서 주로 사용.

### 2-6. on-device vs 자체 운영 서버(vLLM) 상세 비교

| 기준             | on-device (llama.cpp/MLC-LLM) | 자체 서버 (vLLM)        |
| ---------------- | ----------------------------- | ----------------------- |
| 현실적 모델 크기 | 1~4B급                        | GPU 예산에 따라 7B~70B+ |
| 네트워크         | 불필요(완전 오프라인)         | 필요                    |
| 개인정보 이동    | 기기 밖으로 안 나감           | 서버로 전송·저장됨      |
| 한계 비용        | 사용자당 $0                   | 요청/시간당 비용 발생   |
| 배치처리 이득    | 없음(유저별 독립 실행)        | 유저 수 늘수록 커짐     |

→ **이 프로젝트에서 실질적으로 갈리는 기준은 프라이버시**. 개인적인 이야기를 다루는 책임을 심각하게 본다면 on-device가 그 문제를 구조적으로 없앰.

- **소형 모델 태깅 + 템플릿 처리의 한계**: 같은 카테고리 안에서 어떤 사실이 해결됐는지 구분 못 함, 복합 메시지 처리 약함, "해결/악화/신규"를 구분 못 함, 카테고리 셋이 항상 불완전함, 템플릿은 장기적으로 식상해짐.
- **절충안**: 분류기는 "저장할 가치가 있는가"만 판단하는 트리아지 용도로 쓰고, 실제 저장은 정제된 원문으로. 매칭이 애매한 경우(활성 fact 2개 이상)에만 소형 생성모델 호출.

## 3. 논의 사항

### 3-1. 5-2(AI 자유대화 보정)는 MVP에서의 제거 필요성

### 3-2. AI 판정이 공정할 수 없는 이유 (근거)

- **표현력 편향**: AI는 "무엇을 했는가"가 아니라 "무엇을 했다고 얼마나 설득력 있게 썼는가"를 판정 — 자동 에세이 채점 시스템이 오래 겪어온 것과 같은 문제.
- **비결정성**: GPU 배치 처리 특성상 같은 입력도 항상 같은 결과가 보장되지 않을 수 있음(연산 순서 차이). 규칙 기반 수식은 항상 동일한 결과.
- **AI를 구슬리는 법을 아는 사람과 모르는 사람의 격차**: 숫자 조작(기존 문제 1)의 텍스트 버전이며 감지가 더 어려움.
- **개별 오판에 이의를 제기할 방법이 없음**: 규칙 기반은 계산 과정을 검증 가능하지만 AI 판정은 재현·설명이 어려움.
- **절차적 공정성 vs 결과적 공정성**: 모든 유저에게 같은 모델·프롬프트를 적용하면 절차는 공정하지만, 표현력 차이 때문에 결과는 공정을 보장 못 함. 규칙 기반 수식은 둘 다 만족.

### 3-3. 결론

> **AI는 판정/점수에 손대지 않고, 대화/서술에만 사용할지에 대한 논의 필요**

이는 기획서 6장("AI가 난이도를 판정하기보다 사용자가 선택")과 같은 논리이며, 5-2에도 동일하게 적용하기로 확정.

### 3-4. 개인화 기억 시스템 최종 3축 평가

| 축                     | 평가                                                                                                                                                                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **애착/이탈방지 효과** | 메커니즘 자체는 근거 있음(반려동물형 앱 선례)이나 이 앱에서 실제 효과는 검증 불가. 이미 동결/복귀 보너스·번아웃 완충 등 기본 이탈방지 장치가 있어 이 기능은 핵심이 아니라 보너스. 잘 만들면 +, 못 만들면 -가 되는 양날의 기능.                                   |
| **기술적 실현 가능성** | 가능. 트리거·저장·매칭 로직은 기존 Spring Boot/JPA 패턴 재사용 가능. LLM 구조화 출력 호출도 검증된 패턴의 변형 수준. 유일하게 새로운 부분은 소형 모델의 fact 매칭 프롬프트 튜닝 정도. vLLM+서버리스 배포는 선택 확장이지 필수 조건 아님(Ollama만으로 완결 가능). |
| **차별화 가치**        | 있음. "AI를 어디에 쓰면 안 되는지 원칙을 세우고 지켰다"는 서사가 차별화 포인트. 다만 이 가치는 코드만 봐서는 잘 드러나지 않고, 설계 근거를 직접 설명할 때 더 잘 전달되는 종류.                                                                                   |

## 5. 용어 정리

| 용어                                     | 설명                                                                                                                                                                                            |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **vLLM**                                 | 오픈소스 LLM을 서버에서 효율적으로 서빙(추론 처리)하기 위한 엔진. 여러 요청을 동시에 묶어 처리(배치 처리)하는 데 특화됨. 모바일 기기에서 돌지 않고 서버(본인 PC나 클라우드)에서 돈다.           |
| **Ollama**                               | 로컬 PC/서버에서 오픈소스 LLM을 간단히 설치·실행하게 해주는 도구. vLLM보다 설정이 가볍고, 개발·프로토타이핑에 적합.                                                                             |
| **on-device 추론**                       | 모델을 사용자의 폰/기기 안에서 직접 돌리는 방식. 완전 오프라인 동작 가능, 네트워크·서버 비용 없음. llama.cpp, MLC-LLM 같은 별도 런타임 필요.                                                    |
| **self-hosted(자체 서버) 추론**          | 상용 API(OpenAI/Claude 등) 대신, 본인이 직접 운영하는 서버에서 오픈소스 모델을 돌리는 방식. vLLM/Ollama가 이 용도.                                                                              |
| **LoRA (Low-Rank Adaptation)**           | 큰 모델 전체를 다시 학습하지 않고, 작은 추가 파라미터(수십~수백MB)만 학습해서 모델의 행동을 특화시키는 경량 파인튜닝 기법. 베이스 모델은 그대로 두고 어댑터만 갈아 끼울 수 있음.                |
| **양자화 (Quantization)**                | 모델 가중치의 정밀도를 낮춰(예: 16비트→4비트) 메모리 사용량과 연산량을 줄이는 기법. 품질은 약간 떨어지지만 훨씬 적은 GPU 메모리로 모델을 돌릴 수 있게 해줌.                                     |
| **VRAM**                                 | GPU에 내장된 메모리. 모델을 GPU에서 돌리려면 모델 크기에 맞는 VRAM이 필요함(부족하면 실행 자체가 안 됨).                                                                                        |
| **구조화 출력 / guided decoding**        | LLM이 자유 형식 텍스트가 아니라 미리 정한 JSON 스키마 등 정해진 형식으로만 출력하도록 디코딩 단계에서 강제하는 기법. 파싱 실패 리스크를 원천 차단.                                              |
| **서버리스 GPU**                         | GPU 서버를 상시 띄워두지 않고, 실제 요청이 들어올 때만 켜지고 처리 후 꺼지는 방식의 호스팅. 요청이 드문 서비스에 비용 효율적.                                                                   |
| **콜드 스타트 (Cold Start)**             | 서버리스 자원이 꺼져있다가 요청이 들어와 다시 켜질 때 발생하는 초기 지연 시간.                                                                                                                  |
| **RAG (Retrieval-Augmented Generation)** | LLM이 답변을 생성하기 전에, 관련된 외부 정보(문서, DB 등)를 검색해서 함께 참고하게 하는 기법. 이 프로젝트 스케일에서는 fact 수가 적어 불필요하다고 판단됨.                                      |
| **벡터DB / 임베딩**                      | 텍스트를 숫자 벡터로 변환(임베딩)해 저장하고, 의미적으로 유사한 텍스트를 빠르게 검색하기 위한 데이터베이스. 대량의 데이터에서 유용하며, 이 프로젝트처럼 유저당 데이터가 적으면 굳이 필요 없음.  |
| **전략 패턴 (Strategy Pattern)**         | 같은 역할을 하는 여러 알고리즘(예: 정량 지표 계산 vs 자가진단 계산)을 인터페이스로 추상화해서, 상황에 따라 갈아 끼울 수 있게 하는 객체지향 설계 패턴.                                           |
| **상태 머신 (State Machine)**            | 객체가 가질 수 있는 상태(예: 기본형/1차진화/최종형)와 상태 간 전이 규칙을 명시적으로 정의하는 설계 방식.                                                                                        |
| **멱등성 (Idempotency)**                 | 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같게 유지되는 성질. 예: 체크인 요청을 중복으로 보내도 하루 1회만 반영되게 하는 것.                                                            |
| **롤링 윈도우 / 이동평균**               | "최근 14일간의 평균"처럼, 고정된 과거 데이터 전체가 아니라 최근 일정 기간의 데이터만 계속 갱신하며 계산하는 방식.                                                                               |
| **연속 배치 처리 (Continuous Batching)** | 여러 사용자의 요청을 하나의 GPU/모델이 동시에 묶어서 처리하는 서빙 기법. vLLM의 핵심 강점 중 하나.                                                                                              |
| **Agent NPC**                            | 정해진 대사를 따라가는 기존 게임 AI와 달리, LLM을 이용해 성격·지식·기억을 바탕으로 스스로 추론하고 반응하는 게임 캐릭터를 부르는 업계 용어.                                                     |
| **절차적 공정성 vs 결과적 공정성**       | 절차적 공정성은 "모두에게 동일한 규칙이 적용됐는가", 결과적 공정성은 "실제 결과가 모두에게 공평한가"를 뜻함. AI 텍스트 판정은 절차는 동일해도, 표현력 차이 때문에 결과가 공평하지 않을 수 있음. |
| **MSA (Microservices Architecture)**     | 하나의 큰 애플리케이션을 여러 개의 독립된 작은 서비스로 나눠 구축하는 아키텍처. 이 프로젝트 규모에선 과함으로 판단됨.                                                                           |
