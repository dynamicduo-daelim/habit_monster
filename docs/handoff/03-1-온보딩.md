# [3-1단계] 온보딩 API + 출석 + HttpGameRepository 시작

> 먼저 `00-공통.md`. 3-0(실제 DB 테스트 · `BalanceConfig` · `WalletService`)이 끝난 상태여야 한다.

## 목표
가입한 사람이 온보딩(카테고리 · 습관 · 목표 고르기)을 끝내면 **서버 DB에 저장**되고, 다음 로그인 때 바로 홈으로 간다.
앱은 `API_BASE_URL`이 있으면 이 단계 API를 서버로 부른다 — **HttpGameRepository를 이 단계에서 처음 만든다.**

## 범위 (명세 v5 "2. 온보딩" + "1. 회원 · 설정"의 출석)
| API | 명세 절 | 비고 |
| --- | --- | --- |
| `GET /categories` | 2 | 응답의 `starter`는 `imageUrl` 대신 **`imageKey`**(D1). `color` · `glyph`는 앱이 안 씀(D3)이지만 명세대로 보내도 됨 |
| `GET /measure-types?categories=ex,st` | 2 | 측정 항목 + 추천 습관. `RANGE` 항목은 `rangeBelow` · `rangeAbove`도 내려 준다 (D-28) |
| `POST /onboarding` | 2 | **`@Idempotent`**(A3). 하나라도 틀리면 아무것도 저장하지 않고 `errors`에 모두 담아 400. 이미 완료 409 `ALREADY_ONBOARDED` |
| `POST /me/attendance` | 1 | 하루 여러 번 불러도 됨 (`INSERT … ON CONFLICT DO NOTHING`), 연속 일수 갱신 |
| `PATCH /me/onboarding` | — | **지운다** (`POST /onboarding`이 대신함). `UserGateFilter.BEFORE_ONBOARDING`에서도 빼고, 앱 `HttpAuthService.completeOnboarding`도 정리 |

## 온보딩 한 트랜잭션에서 만드는 것 (DB v1.7)
`users.onboarded_at` 기록과 함께:
- `habit.habit_user` (사용자 잠금 · 연속 출석 행), 고른 카테고리마다 `habit.user_category`(`opened_via='INITIAL'`, Lv.1)
- 습관마다 `habit.habit`(ACTIVE) + `habit.habit_period`(seq 1, 기간 코드 · 목표값 · 시작일 = 오늘)
- `goal.goal_user` + 목표들 (`goal.goal`, 이번 주 / 이번 달 기간 — `BusinessDates.weekStart()` · `monthStart()`)
- `monster.monster_user` + **카테고리마다 스타터 몬스터** `monster.user_monster` + `monster.starter_grant` + `monster.dex_entry`(가진 종)
  - 대화 상대(`is_partner`): 운동(ex)을 골랐으면 그 몬스터, 아니면 고른 카테고리 중 `sort_order`가 가장 앞선 것
  - 필드 최대 마리 수는 `BalanceConfig`(field_max)
  - **시작 전 확인: DB 시드가 앱의 새 28종으로 갱신됐는지** (`00-공통.md` 9장). 앱은 6개 카테고리 모두 스타터가 있다 (ex `monkey` · st `mouse` · fd `turtle` · md `koala` · sl `squirrel` · mn `redpanda`). 시드가 옛 5종이면 진행하지 말고 사용자에게 알린다
- `wallet.wallet`(잔액 0) · 필요한 `shop.inventory` 행

모듈 경계: 온보딩을 처리하는 서비스(예: `onboarding/OnboardingService`)가 각 모듈 서비스(habit · goal · monster · wallet)를 **잠금 순서대로** 부른다 (00-공통 6장).

## 사용자에게 확인할 것
- **시작 골드 · 성실볼**: 앱은 시작 골드 50 · 볼 3개(`economy.dart` `startingGold` · `startingBalls`)를 준다. DB 시드에는 해당 설정 키와 원장 사유(지급 사유 코드)가 없다 → 줄지, 준다면 DB에 어떤 키 · 사유를 더할지 사용자에게 제안 (DB는 사용자가 고친다)
- 스타터가 없는 카테고리 처리 (위)

## 앱 작업
- `frontend/lib/core/state/http_game_repository.dart` 새로 — `GameRepository` 구현. 이 단계는 `completeOnboarding`만 서버로, **나머지 메서드는 일단 `LocalGameRepository`에 넘긴다**(다음 단계에서 하나씩 서버로). 넘기는 메서드는 주석으로 "3-x에서 서버로" 표시
- `app.dart`: `AppConfig.useServer`면 `HttpGameRepository`(같은 `ApiClient` — `HttpAuthService`가 `TokenSource`), 아니면 `LocalGameRepository`. `ApiClient.onBusinessDateChanged` → `repository.load()`
- 온보딩 화면은 앱 `Catalog` 카테고리/측정 항목을 그대로 써도 된다 (코드가 DB와 같음). 서버로 보낼 때 측정 항목은 `measureTypeId`로 바꿔야 함 → `GET /measure-types` 응답으로 (카테고리, 순서) → id 표를 만들거나, 앱에 id를 두는 방법 중 하나를 골라 결정 기록에
- 온보딩 완료 응답 후 앱 `GameState`에 반영 (스타터 · 대화 상대 · 습관 · 목표). 3-2의 `load()`가 생기면 그걸로 다시 불러와도 됨
- 앱 시작/복귀 시 `POST /me/attendance` (서버 모드 + 온보딩 완료일 때)

## 테스트 (서버, 실제 DB)
- 정상 온보딩 → 위 행들이 모두 생김, `GET /me`의 `onboarded` true, 온보딩 전 차단(403)이 풀림
- 검사 실패 여러 개 → 400 + `errors`에 모두, **DB에 아무것도 안 남음**
- 두 번 → 409 `ALREADY_ONBOARDED`, 같은 `Idempotency-Key`로 재전송 → 첫 응답 그대로
- 카테고리 1 ~ 3개 · 습관 1 ~ 5개 · 측정 항목이 그 카테고리 것 · 이름 1 ~ 30자 · 목표값 범위 · 주간 0 ~ 3 / 월간 0 ~ 1
- 출석: 같은 날 여러 번 → 1행, 연속 일수 · 최장 연속
- 앱: `HttpGameRepository` 단위 테스트(MockClient)로 요청 모양 확인, 기존 91개 통과

## 완료 기준
위 테스트 통과 + `backend/README.md` API 표 갱신 + 결정 · 작업 기록. 에뮬레이터 확인은 가능하면 (서버 8081 + `--dart-define=API_BASE_URL=http://10.0.2.2:8081/api/v1`).
