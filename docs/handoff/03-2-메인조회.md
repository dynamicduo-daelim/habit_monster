# [3-2단계] 메인 화면 조회 API → 앱이 서버 데이터로 시작

> 먼저 `00-공통.md`. 3-1(온보딩 · HttpGameRepository 뼈대)이 끝난 상태.

## 목표
서버 모드에서 앱을 켜면 **샘플 데이터(DAY 12 · 연속 11일 · 샘플 몬스터)가 아니라 내 서버 데이터**로 홈이 그려진다. 이 단계는 **조회(GET)만** 만든다.

## 범위 (명세 v5 "3. 상단 바 · 메인 화면")
| API | 비고 |
| --- | --- |
| `GET /me/status` | 상단 바: 업무 날짜 · 연속 출석 · 골드 · 볼 개수 · 오늘 체크인 여부 · 남은/전체 탐색 · 기간 끝난 습관 수. 체크인 전엔 탐색 0/0 |
| `GET /me/today` | 오늘 요약: 습관별 보상 기준(첫 제출) 값 · 점수 · 반영 여부 · 채운 날/기간. 체크인 전이면 보상 필드 null |
| `GET /monsters?location=FIELD\|BAG` | 생략하면 전체. 이미지 URL 대신 **`imageKey`**(D1) + 종 코드 |
| `GET /monsters/{id}` | 팝업. `expToNextLevel` → **`expRequired`**(B2). 남의 몬스터면 **404**(C3). 오늘 쓰다듬기/놀아주기 여부(`monster.affection_action`, 업무 날짜 기준) |
| `GET /shop/items` | 시드의 가격 · 효과 (`shop.shop_item`, `is_active`) + 현재 골드 |
| `GET /inventory` | 가방 아이템 (`shop.inventory`, 0개는 빼도 됨 — 결정 기록에) |

규칙 메모
- 연속 출석: `habit.habit_user.current_streak`, 단 `last_attended_date`가 어제보다 이전이면 0으로 보여준다 (schema 주석)
- 호감도 단계(LOW/MID/HIGH)는 `BalanceConfig`의 `affection_tiers`로 계산
- 몬스터 레벨 · 진화 단계는 `monster_exp_per_level` · `evolve_levels`로. 다음 진화 레벨(최종이면 null)
- 모듈 경계: `/me/status`처럼 여러 모듈(habit · wallet · shop · monster)을 모으는 조회는 조회 전용 서비스가 **각 모듈 서비스의 읽기 메서드**를 불러 모은다

## 앱 작업
- `GameRepository.load()`를 `HttpGameRepository`에서 구현: 위 API로 `GameState`를 채운다
- 서버 모드에서는 `GameState.sample()` 대신 **빈 상태**로 시작하고 `load()` 후 그린다 (로딩 표시). 로그아웃하면 다시 빈 상태
  - `GameState`에 "서버 응답을 반영하는" 메서드를 둔다 (예: `applyStatus`, `applyMonsters`). 규칙 메서드는 그대로
- 서버 id ↔ 앱 모델: 몬스터 `uid` = 서버 `userMonsterId` 문자열, 종 = 종 코드(`Catalog.speciesById(code)`), 아이템 = `Catalog.itemByServerCode`
- 앱 `GameState`에 있지만 서버에 없는 값 정리 → **사용자에게 확인**: 상단 바의 `DAY n`(`dayCount` — 가입 후 며칠? 체크인한 날 수? 숨김?)
- 앱 시작 순서: 로그인 복원 → (온보딩 완료면) `load()` + `POST /me/attendance` → 홈

## 테스트
- 서버: 온보딩 직후 사용자 기준 각 API 응답 모양 · 값 (명세 예시와 필드 이름 일치), 남의 몬스터 404, 온보딩 전 403
- 앱: `HttpGameRepository.load()`가 MockClient 응답으로 `GameState`를 채우는 테스트, 기존 테스트 통과
- 가능하면 에뮬레이터: 온보딩 → 홈에 내 스타터 몬스터 · 골드가 보임

## 완료 기준
서버 모드 앱이 샘플 데이터 없이 서버 데이터로 홈을 그린다 + 문서 갱신
