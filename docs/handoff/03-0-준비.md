# [3-0단계] 게임 API를 만들기 전 준비 — 실제 DB 테스트 · 설정값 · 지갑 · 모듈 규칙

> 먼저 `00-공통.md`를 읽는다. 이 단계는 API를 만들지 않는다. 3-1부터 모든 단계가 쓰는 바닥을 만든다.

## 왜 필요한가
- 지금 서버 테스트는 **H2(메모리 DB) + JPA가 엔티티로 만든 테이블**로 돈다. 게임 테이블은 PostgreSQL 전용 제약 · 트리거 · 시드 데이터(카테고리 · 몬스터 · 설정값)에 기대므로 H2로는 제대로 검사할 수 없다 (0단계에서 H2는 통과하고 PostgreSQL에서만 난 버그가 실제로 있었다).
- 게임 규칙의 수치는 `config.balance_config`에 있다 (DB 원칙 4). 읽는 도구가 아직 없다.
- 골드 증감(지갑 + 원장)은 체크인 · 탐색 · 상점 · 목표가 모두 쓴다. 한 곳에 만들어 둔다.

## 시작 전에 사용자에게 물을 것 (계획을 보여줄 때 같이)
1. **테스트가 쓸 공식 SQL의 위치**
   - 지금 공식 SQL은 `docs/데이터베이스/`에 있다 (사용자가 옮김). git에 올라가 있는지 먼저 확인 (`git ls-files docs/데이터베이스`)
   - (추천) A. git에 올려 버전 관리 — 팀원 PC · 나중의 CI에서도 테스트가 돈다. 사용자가 DB 설계의 주인이라 원본도 저장소에 두는 게 자연스럽다. (예전 규칙 "원본은 저장소 밖"을 바꾸는 결정 → 결정 기록에)
   - B. 사용자 PC에만 두고, 테스트가 환경변수 `HM_DB_DIR` 경로에서 읽음 (없으면 건너뜀)
2. **테스트용 PostgreSQL 띄우는 방법** — 새 의존성이므로 허락받는다
   - (추천) Testcontainers (`org.springframework.boot:spring-boot-testcontainers` + `org.testcontainers:postgresql`): 테스트가 `postgres:16` 컨테이너를 스스로 띄우고 공식 SQL을 적용. 다른 사람 PC에서도 Docker만 있으면 됨. 테스트 클래스끼리 컨테이너 하나를 재사용해 느려지지 않게.
   - 대안: 이미 떠 있는 Docker DB(5434)에 붙어서 테스트마다 데이터 정리 — 의존성은 없지만 로컬 DB를 지워 버린다.
3. **모듈 규칙 검사 도구** — ArchUnit(새 의존성) 또는 직접 쓴 간단한 검사 테스트

## 할 일
1. **테스트 기반** `src/test/java/kr/habitmonster/support/PostgresTest` (가칭)
   - 공식 `schema.sql` → `seed.sql` 적용된 PostgreSQL로 `@SpringBootTest` 컨텍스트를 띄우는 공통 베이스 (`ddl-auto=none`)
   - 테스트마다 사용자 데이터 정리 유틸 (자식 → 부모 순서. 마스터 데이터 · 설정값은 남김)
   - 기존 `AuthApiTest` · `CommonApiTest`도 이 베이스로 옮길지 결정 (추천: 옮겨서 진실은 PostgreSQL 하나. 옮기면 H2용 엔티티(`IdempotencyRecord`)와 `application-local.properties`의 create-drop은 `bootRun` 로컬 실행용으로만 남는지 확인)
2. **설정값 읽기** `config/BalanceConfig` (가칭)
   - `config.balance_config`(값은 JSONB)를 시작할 때 읽어 메모리에 두고, 타입 있는 getter 제공 (예: `int exploreDailyFree()`, `double exploreMissRate()`, `Map<Integer, Double> captureRate()`, `Map<String, Double> periodMultiplier()`)
   - 키 목록은 `seed.sql` 마지막 INSERT 참고. 없는 키면 시작 시 실패 (조용히 기본값 쓰지 않기)
   - 앱 `frontend/lib/core/constants/economy.dart`와 수치가 다른 곳이 있으면 목록으로 보고 (서버가 기준, 앱은 서버 없는 모드용)
3. **지갑 모듈** `wallet/` — `WalletService`
   - `credit(userId, amount, reasonCode, refId)` / `debit(userId, amount, reasonCode, refId)` → 잔액(`wallet.wallet`) + 원장(`wallet.wallet_ledger`) 한 줄. 금액 0이면 아무것도 안 함.
   - 차감은 조건부 UPDATE(`… SET balance = balance - ? WHERE user_id = ? AND balance >= ?`) → 0행이면 422 `NOT_ENOUGH_GOLD`
   - 같은 `(reason_code, ref_id)`가 이미 있으면 두 번 지급하지 않음 (UNIQUE 위반을 "이미 처리됨"으로)
   - 사유 코드는 `wallet.ledger_reason` 시드 그대로 (CHECKIN · LEVELUP · PERIOD_BONUS · GOAL_WEEKLY · GOAL_MONTHLY · DUPLICATE · SHOP_PURCHASE · ADJUST). `ref_id` 규칙은 schema.sql 주석
4. **모듈 패키지 규칙** — 서버 패키지 = DB 스키마: `habit` · `goal` · `wallet` · `shop` · `monster` · (나중에 `ai`)
   - 각 패키지 안: 엔티티 · 저장소(repository) · 서비스 · 컨트롤러. **저장소는 자기 스키마 테이블만** 다룬다. 다른 모듈 데이터는 그 모듈 서비스 호출.
   - 이 규칙을 검사하는 테스트 하나 (엔티티의 `@Table(schema=…)`와 패키지가 맞는지, 다른 모듈 저장소를 직접 쓰지 않는지)
5. `ErrorCode`에 명세 "에러 코드 목록"의 코드를 미리 다 넣을지는 단계마다 필요할 때 넣는 쪽을 추천 (안 쓰는 코드가 쌓이지 않게)

## 완료 기준
- `.\gradlew.bat test`가 실제 PostgreSQL(v1.7 스키마 + 시드)에서 돈다 — 기존 25개 포함 전부 통과
- `BalanceConfig`가 시드의 키를 모두 읽고, 없는 키에 실패하는 테스트
- `WalletService` 테스트: 적립 · 차감 · 잔액 부족 422 · 같은 ref 두 번 → 한 번만 · 동시 차감 두 건이 와도 음수 안 됨
- 모듈 규칙 검사 테스트 통과
- 문서: `backend/server/README.md`(테스트 방법 · 구조) · 결정 기록(SQL 위치 · 테스트 방식 · 의존성) · 작업 기록 · 계획 체크박스

## 하지 말 것
- 게임 API를 미리 만들지 않는다 (3-1부터)
- DB 파일(`schema.sql` 등)을 고치지 않는다 — 필요하면 사용자에게 제안
