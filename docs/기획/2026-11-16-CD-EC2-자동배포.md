# CD: 서버를 EC2에 자동 배포 (GitHub Actions)

- 날짜: 2026-11-16
- 상태: 확정 (사용자 11-16 확인 — 미결 항목은 Claude 제안대로. 다음: 사용자 준비 → 구현)
- 관련: 결정 D-76 · D-73 ~ D-75(CI · 브랜치 보호) · D-65(EC2 systemd) · `docs/기획/2026-10-28-배포-EC2-Supabase.md` · `backend/server/README.md` "EC2 배포 서버"

> 추측으로 채운 내용은 **[가정]**. 구현하다 달라지면 이 문서를 고친다.

## 1. 왜 만드나
- **문제**: 지금 배포는 PC에서 `./gradlew bootJar` → `scp` → EC2에 접속해 `systemctl restart`를 손으로 한다. 단계가 많아 순서를 틀리기 쉽고(11-12 DB 옮길 때도 명령 실수가 여러 번 있었다), 새 jar가 안 뜰 때 되돌리는 것도 손으로 해야 한다.
- **목표**: GitHub의 버튼 하나로 `dev` 최신 코드를 빌드 → 전송 → 교체 → 재시작 → 살아 있는지 확인까지 하고, 안 뜨면 이전 jar로 되돌린다.
- **하지 않는 것**
  - 앱(APK) 배포 — 릴리스 서명 키를 커밋하지 않는 구조라 따로 다룬다
  - `dev` 머지 때마다 자동 배포 — DB 계약이 바뀐 jar를 SQL 적용 전에 올리면 서버가 못 뜬다 (D-76)
  - DB(Supabase) SQL 자동 적용 — 사람이 먼저 한다
  - EC2 · Nginx · 인증서 · `app.env` 설정 변경 — 한 번 해 둔 것을 그대로 쓴다
  - 수동 배포 절차 삭제 — README에 그대로 남긴다 (CD가 막혔을 때의 대비책이자 발표 설명용)

## 2. 누가 · 언제 쓰나
- 사용자: 서버 담당(송윤서), 필요하면 팀원. 저장소 관리자(admin)만 워크플로를 실행할 수 있다 **[가정: 쓰기 권한자 전체가 아니라 admin만으로 제한은 하지 않음 — 정해야 할 것 8장]**
- 상황: 서버 코드를 `dev`에 머지했고, DB 계약이 바뀌었으면 Supabase에 SQL을 먼저 적용한 뒤, 실제 서버에 반영하고 싶을 때
- 사용 흐름:
  1. 서버 PR이 `dev`에 머지된다 (CI `backend-test` 통과)
  2. DB 계약이 바뀌었으면 Supabase SQL 편집기에서 SQL을 먼저 적용한다 (사람)
  3. GitHub → Actions → "CD Backend" → **Run workflow** → "DB SQL 적용을 확인했다" 체크 → 실행
  4. 러너가 아래 3장 순서로 배포하고, 끝나면 결과(성공 / 되돌림)가 Actions 화면에 남는다
  5. 필요하면 폰이나 `curl.exe`로 한 번 더 확인한다 (README 명령)

## 3. 규칙

배포 순서 (한 job, `production` Environment):

1. `dev` 브랜치에서 실행했을 때만 진행한다. 다른 브랜치면 즉시 실패
2. 입력 "DB SQL 적용 확인"이 체크돼 있어야 한다. 아니면 즉시 실패 (실수 방지). 입력 "되돌림 연습"(`rollback_drill`, 기본 꺼짐)을 켜면 진짜 jar 대신 **일부러 깨진 파일**을 올려 서버가 못 뜨고 이전 jar로 되돌아오는지 시험한다 **[구현 중 추가 — 7장의 되돌림 시험을 운영 jar 건드리지 않고 하려고]**
3. JDK 21로 `./gradlew bootJar` (테스트는 건너뜀 — 머지 전에 CI가 이미 통과했고 `dev`는 보호돼 있다 **[가정]**)
4. 러너의 공개 IP를 알아내 EC2 보안 그룹 22번에 `/32`로 **임시 허용**
5. jar를 EC2의 `~/app-new.jar.tmp`로 전송 (scp)
6. EC2에서: `app-new.jar` → `app-prev.jar`로 백업, 새 jar를 `app-new.jar`로 교체, `sudo systemctl restart habit-monster`
7. 최대 60초, 5초 간격으로 `https://api.habitmonster.me/api/v1/me/status`를 확인 — **401**이면 성공 (Nginx → Spring까지 도달, README와 같은 판정)
8. 성공이 아니면: `app-prev.jar`를 `app-new.jar`로 되돌리고 다시 시작 → 작업은 **실패**로 끝낸다 (되돌린 것이 눈에 띄게)
9. **성공이든 실패든 취소든** 마지막에 4번의 임시 허용을 반드시 지운다 (`if: always()`)

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 트리거 | 수동(`workflow_dispatch`)만 | D-76 — SQL 적용 순서를 사람이 확인 |
| 실행 환경 | GitHub Environment `production` | 시크릿을 이 환경에만 두고, 필요하면 승인자를 붙일 수 있다 |
| 동시 실행 | 하나만 (`concurrency`, 취소 안 함) | 두 배포가 같은 jar를 동시에 덮어쓰지 않게 |
| 응답 확인 | 60초 · 5초 간격 | 메모리 908MB · `-Xmx256m`에서 시작이 느릴 수 있음 **[가정: 실제 시작 시간은 안 재 봄]** |
| 임시 허용 | 포트 22 · 러너 IP `/32` · 설명 `gha-deploy` | 평소 22번은 "내 IP만" 유지 (배포 기획서 4-1) |

필요한 시크릿 · 설정 (GitHub → Settings → Environments → `production`). **지금은 하나도 안 넣었다.**

| 이름 | 종류 | 내용 |
| --- | --- | --- |
| `EC2_SSH_KEY` | Secret | 배포 **전용** 새 SSH 개인키 (개인 `.pem` 재사용 금지). 공개키는 EC2 `authorized_keys`에 추가 |
| `AWS_ACCESS_KEY_ID` · `AWS_SECRET_ACCESS_KEY` | Secret | 배포 전용 IAM 사용자 — **해당 보안 그룹의 22번 규칙 추가 · 삭제 권한만** |
| `EC2_HOST` | Variable | `16.179.63.74` (탄력적 IP) |
| `EC2_USER` | Variable | `ubuntu` |
| `AWS_REGION` | Variable | `ap-southeast-2` (시드니) |
| `EC2_SECURITY_GROUP_ID` | Variable | EC2 인스턴스의 보안 그룹 ID |

IAM 권한은 `ec2:AuthorizeSecurityGroupIngress` · `ec2:RevokeSecurityGroupIngress`를 **그 보안 그룹 하나에만** 준다 (+ 읽기 `ec2:DescribeSecurityGroups`). EC2를 끄거나 지울 권한은 주지 않는다.

## 4. 화면
- 앱 화면 변경 없음.
- GitHub Actions 탭에 "CD Backend" 워크플로가 생기고, **Run workflow** 버튼에 "DB SQL 적용을 확인했다" 체크박스가 뜬다. 새로 만드는 것.

## 5. 예외 · 경계
- **DB 계약이 바뀐 jar를 SQL 없이 배포** → 새 jar가 시작 실패 → 7번 확인이 실패 → 8번 되돌림. 입력 체크박스가 1차 방어, 되돌림이 2차 방어
- **되돌릴 `app-prev.jar`가 아직 없음 (첫 CD 실행)** → 7번이 실패해도 되돌릴 수 없다. 첫 실행 전에 사용자가 EC2에서 현재 jar를 `app-prev.jar`로 복사해 둔다 (안내를 문서에 넣음)
- **되돌림도 실패** → 작업은 실패로 끝나고, 사람이 README의 수동 절차 · `journalctl -u habit-monster`로 복구한다. 이 경우를 위해 수동 절차를 남긴다
- **작업이 중간에 취소 · 타임아웃** → 9번의 정리가 `always()`로 돌지만, 러너가 갑자기 사라지면 22번 임시 허용이 남을 수 있다. 설명 `gha-deploy`로 찾아서 지운다 — 배포 뒤 보안 그룹 확인을 완료 기준에 넣음
- **임시 허용이 퍼지기 전에 접속** → 허용 직후 몇 초 기다렸다가 접속 **[가정: 5초 대기 후 재시도 몇 번]**
- **Supabase 무료 프로젝트가 멈춰 있음** → 새 jar가 시작 실패 → 되돌림도 같은 이유로 못 뜰 수 있다. 배포 전에 깨워 둔다 (배포 기획서 4장)
- **이 PC 규칙**: Claude는 EC2에 SSH로 접속하지 않는다. AWS 콘솔 · IAM · 키 · 시크릿 등록은 사용자가 하고, Claude는 단계 안내를 쓴다 (메모리 `user-deploys-ec2-themselves`)
- **공개 저장소**: 포크에서 온 PR의 워크플로는 시크릿에 접근하지 못한다. 이 워크플로는 `workflow_dispatch`뿐이라 PR로 실행되지 않는다

## 6. 다른 곳에 미치는 영향
- 앱: 없음
- 서버 · DB: 코드 변경 없음. EC2에 `authorized_keys` 한 줄(배포 전용 공개키)과 `app-prev.jar`가 생긴다. 보안 그룹은 평소엔 그대로 (22번 임시 허용은 배포 중에만)
- 새 파일: `.github/workflows/cd-backend.yml`
- 문서: `backend/server/README.md`에 "자동 배포(CD)" 절을 **추가**(수동 절차는 그대로) · `결정-기록.md`(D-76, 이미 씀) · `작업-기록.md` · `프로젝트-이해.md`(CI/CD 설명이 없으면 추가)

사용자가 먼저 할 준비 (Claude는 대신 못 함 · 안내만):
1. AWS 콘솔: 배포 전용 IAM 사용자 + 위 최소 권한 정책 + 접근 키 발급
2. PC에서 배포 전용 SSH 키 한 쌍 생성 (`ssh-keygen`), 공개키를 EC2 `~/.ssh/authorized_keys`에 한 줄 추가
3. EC2에서 `cp ~/app-new.jar ~/app-prev.jar` (첫 되돌림용)
4. EC2에서 `sudo systemctl restart habit-monster`가 **비밀번호 없이** 되는지 확인 (`ubuntu` 사용자의 sudo 설정) **[가정: 된다]**
5. GitHub → Settings → Environments → `production` 만들기 → 위 3장 Secret · Variable 등록
