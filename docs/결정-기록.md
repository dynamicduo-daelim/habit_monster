# 결정 기록

무언가를 **정할 때마다** 한 건씩 맨 위에 추가한다. 발표에서 "왜 그렇게 했나요?"라는 질문에 답하기 위한 문서다.

쓰는 법:
- 송윤서가 정한(송윤서 작업에서 나온) 결정은 제목 끝에 `(송윤서)`를 붙인다.
- **무엇과 비교했는지**를 꼭 적는다. 비교 대상이 없으면 결정이 아니라 그냥 사실이다.
- 이유를 모르면 지어내지 말고 "이유 미기록"이라고 쓴다. 나중에 채운다.
- 결정이 뒤집히면 지우지 말고 새 건을 쓰고, 옛 건에 "→ D-00으로 바뀜"이라고 적는다.

```
## D-번호. 제목 (YYYY-MM-DD)
- 상황: 무엇을 정해야 했나
- 선택지: A / B / …
- 결정: 무엇으로 정했나
- 이유: 왜
- 영향: 바뀐 코드 · 문서, 남은 일
```

## D-71. 느린 응답 — 서버를 옮기지 않고 DB(Supabase)를 서버 옆 시드니로 옮김 (2026-11-12) (송윤서)

- 선택지
  - (가) EC2를 서울 · 도쿄로 새로 만들기 — 폰 ↔ 서버까지 가까워져 가장 빠름. 대신 IP · 서버 설정을 다시. **AWS 무료 플랜 계정이라 다른 리전에 인스턴스를 못 만듦** ("다른 상용 AWS 리전에 액세스하려면 먼저 플랜을 업그레이드") → 유료 플랜으로 올려야 함
  - (나) 다른 클라우드(예: 오라클 무료 등급 서울)로 서버 이전 — 계정 · 설정 처음부터, IP도 바뀜
  - **(다) 서버는 시드니 그대로, Supabase를 시드니에 새로 만들어 데이터를 옮김** — 무료, IP · 앱 주소 그대로. 폰 ↔ 시드니 왕복(약 0.3초)은 남음
- 결정: (다) — 사용자 11-12 (처음엔 (가)를 골랐으나 무료 플랜 제한으로 (다))
- 이유: 느린 것의 대부분은 **서버 ↔ DB 왕복이 요청마다 여러 번** 쌓인 것이라, 서버와 DB를 같은 리전에 두면 그 부분이 거의 0이 된다. 남는 폰 ↔ 서버 거리는 요청당 한 번뿐이다. 돈 · 주소를 바꾸지 않고 할 수 있는 것 중 효과가 가장 크다

- 영향: Supabase 프로젝트가 바뀜(새 연결 정보 — EC2 `app.env`만), 도쿄 프로젝트는 며칠 뒤 정리. 원칙: **서버와 DB는 같은 리전에.** 나중에 서버를 한국 가까이 옮기면 DB도 같이. 기획서 `2026-10-28-배포-EC2-Supabase.md` 8장, `backend/server/README.md`
