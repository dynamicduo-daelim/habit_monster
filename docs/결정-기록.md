# 결정 기록

무언가를 **정할 때마다** 한 건씩 맨 위에 추가한다. 발표에서 "왜 그렇게 했나요?"라는 질문에 답하기 위한 문서다.

쓰는 법:
- 송윤서가 정한(송윤서 작업에서 나온) 결정은 제목 끝에 `(송윤서)`를 붙인다.
- **무엇과 비교했는지**를 꼭 적는다. 비교 대상이 없으면 결정이 아니라 그냥 사실이다.
- 이유를 모르면 지어내지 말고 "이유 미기록"이라고 쓴다. 나중에 채운다.
- 결정이 뒤집히면 지우지 말고 새 건을 쓰고, 옛 건에 "→ D-00으로 바뀜"이라고 적는다.

```
## D-번호. 제목 (YYYY-MM-DD)
- 상황: 무엇을 정해야 했나
- 선택지: A / B / …
- 결정: 무엇으로 정했나
- 이유: 왜
- 영향: 바뀐 코드 · 문서, 남은 일
```

## D-32. DB 시드 v1.8: 몬스터를 앱의 28종으로, 종 번호는 카테고리 순서 (2026-10-17) (송윤서)

## D-29. 이메일 하나에 계정 하나 + 검증된 소셜 이메일만 사용 (2026-10-15) (송윤서)
- 상황: 10-07에는 "같은 이메일이어도 이메일 계정과 소셜 계정은 다른 계정"(Q-20)이었다. API 명세 v4~5와 DB v1.7은 `users.email`을 계정당 하나로 바꿨다.
- 선택지: 같은 이메일이면 자동으로 합치기 / 막고 원래 가입 방법 안내 / 예전처럼 따로 두기
- 결정: 막고 안내 (409 `EMAIL_REGISTERED_WITH_OTHER_METHOD` + `provider`). 소셜 이메일은 제공자가 **검증한 것만** 계정 이메일로 쓰고, 검증 안 됐으면 이메일 없이 가입 (C4).
- 이유: 이메일 가입은 인증 메일이 없어서, 자동으로 합치면 남의 이메일로 먼저 가입해 두고 나중에 그 사람의 소셜 계정을 가로챌 수 있다. 검증 안 된 소셜 이메일을 쓰면 반대로 남의 이메일을 막아 버릴 수 있다.
- 영향: Q-20 폐기. `AuthService.rejectTakenEmail` · `SocialIdentity.verifiedEmail()`. 남은 위험: 남의 이메일로 이메일 가입을 먼저 해 두면 그 사람은 소셜로 가입할 수 없다 (명세 「보류 항목」의 "이메일 선점").

## D-27. 중복 방지 키는 공식 `api.idempotency_record`로, 동작 방식(D-25)은 유지 (2026-10-15) (송윤서)
- 상황: DB v1.7에 중복 방지 키 테이블이 들어왔다. 0단계에서 우리가 만든 `identity.idempotency_record`와 역할이 같다. 공식 테이블은 처리 중에 처리 기한(`locked_until`, 30초)을 두는 방식이고 응답 본문은 JSONB다.
- 선택지: 우리 테이블 유지 / 공식 테이블 + 공식 방식(기한이 지나면 다시 잡기) / 공식 테이블 + 우리 방식(행 잠금)
- 결정: 공식 테이블 + 행 잠금. `locked_until`은 제약을 지키고 운영자가 볼 수 있게 채워 둔다. `server_additions.sql` 삭제.
- 이유: DB는 공식 설계가 기준이다. 판단은 행 잠금이 더 안전하다 — 기한 방식은 30초 안에 처리가 안 끝나면 두 번 실행될 수 있다.
- 영향: `IdempotencyStore`(테이블 · 컬럼 이름, PostgreSQL은 `cast(? as jsonb)`), 경로는 `/api/v1`을 포함한 전체 경로로 저장. JSONB라 다시 보낼 때 응답의 키 순서 · 공백은 바뀔 수 있다 (내용은 같음). D-26의 "서버 추가분" 부분은 이 결정으로 바뀜.

## D-25. 중복 방지 키: 요청 전체를 트랜잭션 하나로 + 행 잠금 (2026-10-15) (송윤서)
- 상황: API 명세 v4는 같은 키면 처음 결과를 돌려주라고 하지만, 처리 중에 서버가 죽거나 결과 저장과 실제 변경 중 하나만 남는 경우는 정하지 않았다 (검토 의견 A2).
- 선택지: ① 컨트롤러마다 직접 처리 / ② 필터에서 처리 + "처리 중" 표시를 60초 뒤 자동 해제 / ③ 필터에서 요청 전체를 트랜잭션으로 감싸고 키 행을 `FOR UPDATE NOWAIT`로 잠금
- 결정: ③. 2xx는 결과를 같은 트랜잭션에 저장해 함께 커밋, 4xx는 변경을 되돌리고 결과만 저장, 5xx는 저장하지 않음. 키가 필요한 API는 `@Idempotent`로 표시.
- 이유: ①은 API마다 같은 코드를 반복하고 빠뜨리기 쉽다. ②는 60초 안에 처리가 안 끝나면 두 번 실행될 수 있다. ③은 서버가 죽으면 DB가 잠금을 풀어 주고, 결과와 변경이 항상 같이 남거나 같이 사라진다.
- 영향: `idempotency/` 패키지, 테이블 `identity.idempotency_record`. 대가: 요청마다 DB 연결을 처음부터 끝까지 잡는다 (트래픽이 적은 지금은 문제 없음). 도메인 테이블의 `idempotency_key` UNIQUE는 마지막 방어선으로 그대로 둔다.
