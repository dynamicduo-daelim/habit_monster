# 루틴몬 — 구현 결정 & 계획 (API 명세 v5 기준)

2026-10-15 · 기준: `D:/teamProject/docs/api/습관몬스터_API명세_v5.md`(저장소 밖) + 현재 코드

> 명세 v5(10-15, @윤서 작성 — DB 설계도 윤서)는 v4에 **도감 "본 종"(`OWNED`/`SEEN`/`UNKNOWN`)**만 더한 판이다. 아래 1장의 결정은 명세에 없는 것을 우리가 구현할 때 더하는 것이며, 명세 버전 번호와는 별개다.

판단 기준은 하나: **"사용자가 매일 열어서 끝까지 쓸 수 있는 앱"을 가장 적은 작업으로.**
그래서 (1) 데이터가 날아가거나 보상이 두 번 들어가는 버그는 지금 막고, (2) 기능은 핵심 루프(체크인 → 탐색 → 포획 → 성장)부터, (3) 없어도 앱이 굴러가는 것은 출시 뒤로 미룬다.

## 1. 명세에 더하는 구현 결정 (결정함)

### A. 꼭 고칠 것 (안 고치면 버그)

| # | 항목 | 결정 |
| --- | --- | --- |
| A1 | 탈퇴 후 액세스 토큰이 살아 있음 | JWT 필터가 매 요청 `users.status` 확인. 탈퇴·없음이면 401 `INVALID_TOKEN` |

| A6 | 범위형(수면) 습관 | ~~MVP에서 범위형 제거~~ → **살린다 (D-20)**: DB v1.7은 범위를 측정 항목의 허용 폭(`range_below/above`)으로 두므로 습관 등록에 칸이 필요 없다 |

### B. 해석이 갈리던 것

| # | 항목 | 결정 | 이유 |
| --- | --- | --- | --- |
| B1 | 기간 채운 날 · 보너스 | `filledDays`는 `done:true`면 반영(상위 3) 여부와 상관없이 +1. 기간을 채우는 날 반영 습관이 아니어도 **보너스 지급** (`periodScore`는 반영된 날의 점수 합이라 이미 공정) | 30일 채웠는데 마지막 날 순위 때문에 보너스를 잃으면 이탈 |
| B2 | `expToNextLevel` | `expRequired`(그 레벨 필요 총량)로 이름 변경. 몬스터·통계 둘 다 | 이름과 값 불일치 |
| B3 | `options` 생성 | 서버가 생성: 목표 × {0.25, 0.5, 0.75, 1, 1.5, 2}를 `step`으로 반올림, 중복 제거, `maxValue` 이하. **목표값은 항상 포함** | 목표값이 없으면 20점을 못 받음 |
| B4 | 탐색 후보 | 명세대로 **연 카테고리 전체** | 초반 후보 부족 완화, 구현 단순 |
| B5 | 초반 탐색 | 종 해금 레벨 **1/1/3/6/10/14/18** (Lv.1에 시작 몬스터 + 1종) | Lv.1이면 탐색해도 골드만 나와서 첫날 재미가 없음 |
| B6 | DB | 공식 스키마는 팀 규칙대로 저장소 밖(`D:/teamProject/docs/데이터베이스`, v1.7)에 두고 Docker가 연결해 적용 (D-18). 서버 추가분은 v1.7에 들어와서 없음 (D-19) | 원본 복사본이 생기면 어긋남 |

| # | 항목 | 결정 |

## 5. 팀에 알리기만 하면 되는 것
위 결정 중 명세 · DB(윤서 작성)의 다음 판에 반영할지 정할 것: B1 · B5 · C1 · D1 · D4 · D6 (A6은 D-20으로 취소). 나머지는 구현 세부라 다음 명세 판에 반영만 하면 된다.
