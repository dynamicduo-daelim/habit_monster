- 상태: **제안** — `docs/데이터베이스/schema.sql`(v1.7) · `seed.sql` · API 명세(v5)는 윤서 님 문서라 직접 고치지 않는다. 합의되면 스키마 v1.9 · 명세 v6에 반영.
- 근거: 기획 `docs/기획/2026-11-04-스토리-이벤트-처리.md` 3-6 · 결정 D-65 (사용자: "기록은 계정 그대로 남게")

## 왜
루틴몬 이야기(웹툰)는 호감도 · 진화 · 도감 수에 따라 열린다. 열린 편과 본 편을 폰에만 두면 폰을 바꾸거나 앱을 다시 깔 때 사라진다 → 계정에 남긴다.

## 무엇이 서버에 필요한가 — 최소
열림 판단(어떤 편이 열려야 하나)은 앱이 이미 서버에서 받은 호감도 · 레벨 · 보유 종으로 계산한다. 서버는 **"이 계정에서 이 편이 열렸다 / 봤다"만 저장**한다. 이야기에는 보상이 없어서 서버가 조건을 다시 검사하지 않아도 된다.

### 표
```sql
-- 모듈: monster (호감도 · 도감과 같은 곳)
CREATE TABLE monster.user_story (
  user_id     BIGINT       NOT NULL REFERENCES monster.monster_user(user_id),
  episode     TEXT         NOT NULL,          -- 편 id: '<종 code>-<1~3>' 또는 'village-<마을>-<1~3>' (예: monkey-1, village-hot-2)
  opened_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
  seen_at     TIMESTAMPTZ,                    -- 처음 끝까지 본 때, 안 봤으면 NULL
  PRIMARY KEY (user_id, episode),
  CHECK (episode ~ '^([a-z]+-[1-3]|village-[a-z]+-[1-3])$')
);
```
- 행은 지우지 않는다 (schema 원칙). 같은 편을 다시 열면 그대로(멱등).
- 편 목록 자체(제목 · 컷)는 앱에 있다 → 서버 표는 id만. 편 id 규칙만 맞추면 된다.

### API (명세 v5 모양을 따름)
| 메서드 · 경로 | 하는 일 | 응답 |
| --- | --- | --- |
| `GET /api/v1/stories` | 이 계정의 열림 · 본 기록 전체 | `{ "items": [ { "episode": "monkey-1", "openedAt": "…", "seenAt": null } ] }` |
| `POST /api/v1/stories/opened` | 편 여러 개를 한 번에 "열림"으로 (기존 사용자 일괄 열림 포함) · `Idempotency-Key` | `{ "opened": ["monkey-1", "village-hot-1"] }` (새로 열린 것만) |
| `POST /api/v1/stories/{episode}/seen` | 한 편을 "봄"으로 (이미 봤으면 그대로) | `{ "episode": "monkey-1", "seenAt": "…" }` |

- 잘못된 편 id → 422. 열리지 않은 편을 "봄"으로 → 열림 · 봄을 같이 기록(앱 순서가 꼬여도 실패하지 않게).
- `GET /home`(또는 앱 첫 `load()`)에 넣을지, 따로 부를지는 윤서 판단. 따로 불러도 하루 한 번 정도.

## 앱 쪽 (서버가 생기면)
- 서버 모드: `load()`에서 `GET /stories` → 열림 판단 결과 중 새 편은 `POST /stories/opened`, 다 보면 `POST /stories/{id}/seen`.
- 서버가 생기기 전: 서버 모드도 임시로 폰에 저장 → 서버가 생긴 날 한 번 `opened`로 올리고 폰 기록 지움.
- 시연 모드(로컬): 폰 저장 그대로.
