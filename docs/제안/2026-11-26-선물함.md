## 1. 흐름
```
퀘스트 완료 (체크인 · 쓰다듬기 · 조회 등 다른 요청 안에서)
  └ quest: user_quest를 DONE으로 (지금과 같음)
     └ gift: 선물 한 줄 INSERT  ← 지갑에 넣지 않음 (전: wallet.credit)

사용자가 선물함에서 "받기"
  └ gift: 선물 행을 "받음"으로 (조건부 — 이미 받았으면 409)
     ├ shop: 아이템이 있으면 가방 +N
     └ wallet: 골드가 있으면 적립 (원장 사유 = 선물 출처, ref_id = 선물 id)
```

## 2. API 명세 (v9 → v10) — 새 장 「11. 선물함 (v10)」

### GET /gifts — 받지 않은 선물
```json
// 응답 200
{
  "gifts": [
    { "id": 42, "source": "QUEST_WEEKLY", "title": "주 4일 출석",  "gold": 5, "itemCode": null,  "itemName": null,    "quantity": 0, "createdAt": "2026-11-26T09:12:00+09:00" },
    { "id": 41, "source": "QUEST_DAILY",  "title": "오늘의 기록",  "gold": 3, "itemCode": null,  "itemName": null,    "quantity": 0, "createdAt": "2026-11-26T08:01:00+09:00" }
  ]
}
```
- **받지 않은 선물만**, 최신순. 받은 선물은 보여 주지 않는다 (받은 골드 내역은 원장에 있다).
- 비었으면 `"gifts": []`. 페이지 나눔 없음 (가장 많이 쌓여도 한 달 약 130개 — 기획서 5장).
- `source`: `QUEST_DAILY` · `QUEST_WEEKLY` (다음 단계에서 `QUEST_MONTHLY` · 업적 · 깜짝이 더해진다). 앱은 아이콘 고르기에만 쓴다.
- 아이템 선물 예 (4단계): `{ "source": "QUEST_MONTHLY", "title": "11월 배지", "gold": 0, "itemCode": "BALL", "itemName": "성실볼", "quantity": 1 }`

### POST /gifts/{giftId}/claim — 받기
- `Idempotency-Key` 필수. 본문 없음. `businessDate` 없음 (날짜에 묶인 행동이 아니어서 — 어제 선물도 오늘 받는다).
```json
// 응답 200
{
  "claimedCount": 1,
  "goldReceived": 5,
  "items": [],
  "gold": 345,
  "ballCount": 2
}
```
- `gold` · `ballCount` = 받은 뒤 지갑 잔액 · 가방의 볼 개수 (상단 바를 바로 고칠 수 있게 — `GET /me/status`와 같은 이름).
- `items` = 받은 아이템 `[{ "itemCode": "BALL", "quantity": 1 }]`.
- 오류
  - 404 `NOT_FOUND` — 없는 선물 · **남의 선물** (C3 — 있는지도 알려 주지 않음)
  - 409 `GIFT_ALREADY_CLAIMED` "이미 받은 선물이에요" — 이미 받은 선물을 **새 요청**으로 다시 받으려 할 때 (다른 기기 · 화면을 새로 고치지 않은 채 다시 누름)
  - 같은 `Idempotency-Key`로 다시 보내면 409가 아니라 **첫 응답(200)을 그대로** 돌려준다 (공통 규칙 — 네트워크가 끊겨 앱이 재시도한 경우)

### POST /gifts/claim-all — 모두 받기
- `Idempotency-Key` 필수. 본문 없음. 응답은 위와 같은 모양 (`claimedCount` = 받은 개수, `goldReceived` · `items`는 합계).
- 받을 선물이 없으면 **200, `claimedCount: 0`** (오류 아님 — 409는 "특정 선물"을 다시 받을 때만).

### GET /me/status — 칸 하나 추가
```json
  "hasGift": true
```
- 받지 않은 선물이 하나라도 있으면 `true` → 홈 선물 아이콘에 점(•). 개수는 내려 주지 않는다 (사용자 결정 — 숫자가 할 일처럼 보이지 않게).

## 3. 잠금 순서 — 받기는 선물 행을 **맨 먼저** 잡는다 (기획서 3-4장의 안을 고침)

기획서에는 "받기: `inventory → wallet → gift`"로 적었다. 그런데 그렇게 하면 "이미 받았는지"를 **가방 · 지갑을 잠근 뒤에야** 알 수 있어, 두 요청이 동시에 오면 둘 다 받지 않은 것으로 읽고 가방에 두 번 넣을 수 있다(그걸 막으려면 선물 행을 미리 따로 잠가야 해서 결국 순서가 깨진다). 그래서:

| 경로 | 순서 |
| --- | --- |
| 받기 · 모두 받기 | **gift**(받을 행을 `id` 순서로 `FOR UPDATE` → "받음"으로) → inventory → wallet |
| 퀘스트 완료 (선물 만들기) | … → wallet → quest → gift (**새 행 INSERT만**, 있는 행을 잠그지 않음) |
| 그 밖 (구매 · 포획 · 체크인 …) | 지금과 같음 (gift를 건드리지 않음) |

- 교착이 생기지 않는 이유: 교착은 "A가 X를 쥐고 Y를 기다리고, B가 Y를 쥐고 X를 기다릴" 때 생긴다. **있는 선물 행을 잠그는 것은 받기뿐이고, 받기는 그것을 가장 먼저 잡는다.** 가방이나 지갑을 쥔 채 선물 행을 기다리는 요청이 없으므로 고리가 생길 수 없다. 퀘스트 경로의 INSERT는 새 행이라 남이 쥔 행을 기다리지 않는다.
- 문서 표기 (안): `gift(받기) → habit_user → goal_user → monster_user → inventory → wallet → quest` + "퀘스트 경로는 gift에 새 행만 넣는다". `schema.sql` 원칙 3-1 · `backend/CLAUDE.md` · `quest/README.md`에 같은 문장.
- 두 기기에서 동시에 받기: 늦은 쪽은 앞쪽이 끝날 때까지 선물 행에서 기다렸다가, "이미 받음"을 보고 409.

## 4. DB (v1.12 → v1.13)
```sql
CREATE SCHEMA gift;

-- 선물 출처 (열린 집합). 골드가 있는 선물의 출처 코드는 원장 사유(CREDIT)에도 있어야 한다 (verify)
CREATE TABLE gift.gift_source (
  code         TEXT          PRIMARY KEY,
  description  VARCHAR(100)  NOT NULL
);
INSERT INTO gift.gift_source (code, description) VALUES
 ('QUEST_DAILY','일일 퀘스트 완료'),
 ('QUEST_WEEKLY','주간 퀘스트 완료');

CREATE TABLE gift.gift (
  id             BIGINT       GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id        BIGINT       NOT NULL REFERENCES identity.users(id),
  source_code    TEXT         NOT NULL REFERENCES gift.gift_source(code),
  source_ref     VARCHAR(64)  NOT NULL,                -- QUEST_* → quest.user_quest.id
  title          VARCHAR(40)  NOT NULL,                -- 만들 때 고정 (퀘스트 제목 등)
  gold           INT          NOT NULL DEFAULT 0 CHECK (gold >= 0),
  item_code      TEXT         NULL REFERENCES shop.shop_item(code),
  item_quantity  SMALLINT     NULL CHECK (item_quantity > 0),
  created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
  claimed_at     TIMESTAMPTZ  NULL,                    -- NULL = 아직 안 받음
  CONSTRAINT uq_gift_source UNIQUE (source_code, source_ref),         -- 같은 출처에서 선물은 하나
  CONSTRAINT ck_gift_item   CHECK ((item_code IS NULL) = (item_quantity IS NULL)),
  CONSTRAINT ck_gift_nonempty CHECK (gold > 0 OR item_code IS NOT NULL)  -- 빈 선물 금지
);
CREATE INDEX ix_gift_unclaimed ON gift.gift (user_id, id DESC) WHERE claimed_at IS NULL;  -- 목록 · hasGift
```
- **트리거** `gift_lock_after_create`: 만든 뒤 내용(사용자 · 출처 · 골드 · 아이템 · 개수)은 못 바꾸고, `claimed_at`은 NULL → 값 한 번만 (되돌리기 금지). 보상 기준값을 트리거로 막는 기존 원칙과 같게.
- **원장 `ref_id` 뜻 바뀜**: `QUEST_DAILY` · `QUEST_WEEKLY` → `gift.gift.id` (전: `quest.user_quest.id`). `schema.sql` 485 · 502 · 503행 주석과 서버 `LedgerReason` 주석.
- **verify S-12 고침**: 가방 수량 = 구매 합 + **받은 선물의 아이템 합** − 사용 합.
- **verify 추가** (S-33 ~ S-35 안): 골드가 있는 선물의 출처는 원장 사유(CREDIT)에 있다 · 받은 선물(골드 > 0)마다 원장 한 줄(사유 = 출처, ref = 선물 id, 금액 = 골드) · 빈 선물 · 내용 수정 · `claimed_at` 되돌리기가 막힌다 · app_core는 gift 읽기 · 쓰기, app_ai는 못 봄.
- **권한**: `schema.sql` 끝의 app_core 스키마 목록에 `gift`.
- **`backend/db/migrate-v1.13.sql`**: 스키마 · 테이블 · 트리거 · 시드 · 권한 (`IF NOT EXISTS` · `ON CONFLICT DO NOTHING`, 두 번 실행해도 안전). ~~맨 앞에 확인: 원장에 `QUEST_*` 줄이 있으면 멈춤 — 0줄일 것으로 예상~~ → **11-26 고침**: Supabase에 옛 방식 줄이 4개 있었다(배포된 서버가 지급). 멈추는 대신 옛 줄마다 **이미 받은 선물**을 만들고 선물 id = 옛 ref_id로 넣는다 — 원장 · 잔액은 그대로. 자세한 이유 · 비교는 `backend/db/README.md` v1.13. **새 서버 배포 직전에 한 번 더** 실행.
- 설정 키 추가 없음.
