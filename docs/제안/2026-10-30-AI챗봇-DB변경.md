## 1. `ai.daily_call_count` (새) — AI 호출 수

```sql
CREATE TABLE ai.daily_call_count (
  user_id     BIGINT       NOT NULL REFERENCES identity.users(id),
  call_date   DATE         NOT NULL,                              -- 업무 날짜 (00:00 경계)
  call_count  SMALLINT     NOT NULL DEFAULT 0 CHECK (call_count >= 0),
  updated_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, call_date)                                -- 하루 1행
);
```
- 한도(`ai_daily_call_limit`)는 config에 두고 CHECK에 넣지 않는다 (역할 나누기 — 8-2).
- 올리기와 한도 검사를 **한 문장**으로 한다 (동시에 두 요청이 와도 넘지 않게):
  ```sql
  INSERT INTO ai.daily_call_count (user_id, call_date, call_count) VALUES (?, ?, 1)
  ON CONFLICT (user_id, call_date) DO UPDATE
    SET call_count = ai.daily_call_count.call_count + 1, updated_at = now()
    WHERE ai.daily_call_count.call_count < ?          -- 한도
  RETURNING call_count;                               -- 행이 안 돌아오면 한도 초과 → 429
  ```
- 다른 테이블을 잠그지 않으므로 잠금 순서와 상관없다. 개인정보가 없는 숫자라 탈퇴 때 지우지 않는다 (`ai.checkin_dialogue`처럼 `identity.users`를 참조).

## 2. `habit.habit_checkin` — 근거 · 점수 상한

```sql
-- schema.sql CREATE TABLE habit.habit_checkin 에 추가
  evidence           TEXT     NOT NULL DEFAULT 'SHORT'
                     CHECK (evidence IN ('SHORT','DETAILED','VERIFIED')),           -- 최신 근거 (다시 체크하면 바뀜)
  rewarded_evidence  TEXT     NOT NULL DEFAULT 'SHORT'
                     CHECK (rewarded_evidence IN ('SHORT','DETAILED','VERIFIED')),  -- 첫 확정 근거 (불변)
  score_capped       BOOLEAN  NOT NULL DEFAULT false,                               -- 최신 점수가 자기보고 상한에 걸려 깎였는지
```
- `rewarded_evidence`는 `rewarded_value` · `rewarded_score`처럼 **수정 금지 트리거**(`habit.forbid_reward_change`) 대상에 넣는다.
- `evidence` · `score_capped`는 `value` · `score`처럼 최신 제출 값이다 (다시 체크하면 바뀜).
- 기존 행은 기본값 `SHORT` · `false`로 채워져 지금 보상과 달라지지 않는다.
- 카테고리 경험치는 `rewarded_score` × 계수를 습관마다 반올림해 더하므로 칸을 더 만들지 않는다 (결과는 기존 `user_category.exp_total`에 들어감).

## 3. `habit.habit_timer` (새) — 습관 타이머

```sql
CREATE TABLE habit.habit_timer (
  id               BIGINT       GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id          BIGINT       NOT NULL REFERENCES habit.habit_user(user_id),
  habit_id         BIGINT       NOT NULL REFERENCES habit.habit(id),
  business_date    DATE         NOT NULL,                    -- 기록되는 업무 날짜: 시작할 때 시작한 날로 넣고, 끝낼 때 ended_at의 업무 날짜로 다시 적는다 (3차)
  status           TEXT         NOT NULL CHECK (status IN ('RUNNING','PAUSED','STOPPED')),
  started_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),      -- 서버 시각
  paused_at        TIMESTAMPTZ  NULL,                        -- 지금 일시정지 중이면 그 시각
  paused_seconds   INTEGER      NOT NULL DEFAULT 0 CHECK (paused_seconds >= 0),
  ended_at         TIMESTAMPTZ  NULL,                        -- 자동 종료면 실제로 끝나야 했던 시각 (경과가 최대 시간에 닿은 시각 · 습관 기간이 끝난 00시)
  end_reason       TEXT         NULL CHECK (end_reason IN ('USER','MAX_DURATION','HABIT_STOPPED')),
  counted_minutes  SMALLINT     NULL CHECK (counted_minutes BETWEEN 0 AND 1440),  -- 끝낼 때 확정. 1440 = 하루 (설정을 어떻게 바꿔도 넘지 않을 값)
  CONSTRAINT ck_timer_end    CHECK ((status = 'STOPPED') = (ended_at IS NOT NULL)),
  CONSTRAINT ck_timer_result CHECK ((status = 'STOPPED') = (counted_minutes IS NOT NULL AND end_reason IS NOT NULL)),
  CONSTRAINT ck_timer_paused CHECK ((status = 'PAUSED') = (paused_at IS NOT NULL)),
  CONSTRAINT ck_timer_order  CHECK (ended_at IS NULL OR ended_at >= started_at)
);
-- 습관마다 끝나지 않은 타이머는 하나 (3차)
CREATE UNIQUE INDEX uq_habit_timer_active  ON habit.habit_timer (habit_id) WHERE status IN ('RUNNING','PAUSED');
-- 실제로 도는 타이머는 한 사용자에 하나 (3차)
CREATE UNIQUE INDEX uq_habit_timer_running ON habit.habit_timer (user_id)  WHERE status = 'RUNNING';
CREATE INDEX ix_habit_timer_day ON habit.habit_timer (user_id, business_date);
```
- 한 번 최대 시간(240분)은 config `timer_max_minutes`에 두고 CHECK에는 넣지 않는다 — CHECK의 1440은 설정을 어떻게 바꿔도 넘을 수 없는 값이라 충돌하지 않는다 (8-2).
- **최대 시간은 일시정지를 뺀 경과 시간 기준** (2차 검토, 3차에서 확정): 경과 = (끝 또는 지금) − `started_at` − `paused_seconds` − (일시정지 중이면 지금 − `paused_at`). 경과가 240분에 닿으면 `MAX_DURATION`, `ended_at` = `started_at` + 240분 + 그때까지의 `paused_seconds`. 일시정지 중에는 경과가 늘지 않으므로 `MAX_DURATION`에 걸리지 않는다.
- **00시에 끝나지 않는다 — 기록은 끝난 날 하나에만** (3차): 끝낼 때 `business_date`를 `ended_at`의 업무 날짜(Asia/Seoul, 경계 00시)로 다시 적는다. 23:30 시작 → 00:12 끝이면 42분 전부 다음 날. 일시정지한 채 날을 넘겨도 같다 (그래서 끝낼 때 `paused_at`을 비우고 그때까지의 일시정지 시간을 `paused_seconds`에 더하기만 하면 됨 — `ck_timer_paused`).
- **습관을 그만두거나 기간이 끝나면** (`habit.habit` 상태 → `STOPPED` · `ENDED`) 그 습관의 끝나지 않은 타이머를 `STOPPED` · `end_reason = 'HABIT_STOPPED'`로 끝낸다 (그때까지 잰 분 기록). 그만두기는 같은 트랜잭션에서, 기간 끝은 다음 요청 때 자동 정리에서 (`ended_at` = 기간이 끝난 00시).
- 오늘 합계 = `SUM(counted_minutes) WHERE user_id = ? AND habit_id = ? AND business_date = ? AND status = 'STOPPED'` — **자동 종료 정리를 먼저 한 뒤** 읽는다.
- 쓸 수 있는 습관(측정 항목 `unit = '분'` · `TARGET_RATIO` · 그만두지 않음)인지는 서버 규칙으로 검사 (스키마 간 검사가 복잡해서 CHECK로 두지 않음).
- 같은 습관에 두 번 시작하면 `uq_habit_timer_active`, 다른 습관 타이머가 도는 중에 시작 · 이어서 재면 `uq_habit_timer_running`이 막는다 (동시 요청이어도 하나만 통과). 위반 → 409 `TIMER_ALREADY_RUNNING`. 일시정지한 타이머는 여러 습관에 남아 있어도 된다.
- 탈퇴 정리: 도는 타이머를 `STOPPED`(`end_reason = 'USER'`)로 바꾸는 일을 habit 모듈의 `WithdrawalStep`에 추가.

## 4. `habit.health_daily` (새, 다음 단계) — 안드로이드 Health Connect

```sql
CREATE TABLE habit.health_daily (
  user_id            BIGINT       NOT NULL REFERENCES habit.habit_user(user_id),
  business_date      DATE         NOT NULL,
  exercise_minutes   SMALLINT     NOT NULL CHECK (exercise_minutes BETWEEN 0 AND 600),
  updated_at         TIMESTAMPTZ  NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, business_date)                        -- 같은 날 다시 올리면 덮어씀
);
```
- **판정에 쓰는 운동 시간만 저장한다.** 걸음 수 · 운동 횟수 · 출처 앱은 저장하지 않는다 (민감정보 최소 수집).
- 앱에서 동의를 받은 사용자만 올린다. 앱이 읽어 보낸 값이라 범위만 검사한다 (완전한 검증 아님 — 기획서 3-6 한계).
- 탈퇴 정리: 건강정보라 탈퇴 때 **이 사용자의 행을 지운다** ("행은 지우지 않는다" 원칙의 예외 — 원칙 7 개인정보 정리와 같은 이유). habit 모듈의 `WithdrawalStep`에 추가.

| 15 | (3차) 00시 자동 종료, `business_date` = 시작한 날 (#6 · #12) | 00시에 안 끝남, `business_date` = **끝난 날** (끝낼 때 다시 적음), `end_reason`에서 `MIDNIGHT` 삭제 | 밤늦게 잰 시간이 버려졌음. 나누지 않으니 날짜는 끝낼 때 한 번만 정함 (사용자: 여러 날에 걸쳐 적용하면 복잡) |
| 16 | (3차) 기간 끝(ENDED)은 00시 종료가 처리 | 자동 정리에서 `HABIT_STOPPED`, `ended_at` = 기간이 끝난 00시 | 00시 종료가 없어짐 |
| 17 | (3차) 반영 순서: 타이머는 나중 (그 전엔 앱 기기에만) | 근거 · 상한 · 설정과 **같은 단계** (6장) | D-62 — 타이머 없이 상한만 나가면 깎이기만 함 |

### 8-2. 알아둘 것

- **DB CHECK와 config의 역할 나누기**
  - CHECK = 절대 바뀌지 않는 사실 (음수 불가, 하루는 1440분).
  - config = 운영하며 바꿀 수 있는 정책 (최대 240분, 하루 60회, 상한 20점).
  - 정책 숫자를 CHECK에도 적으면, config만 바꿨을 때 서버는 된다고 하고 DB는 거부해서 오류가 난다.
  - 기존 설계도 이렇게 되어 있다: `habit_checkin.score`는 CHECK가 `>= 0`뿐이고 25는 `score_max`, `user_monster.affection`도 `>= 0`뿐이고 10은 `affection_max`.
- **DETAILED는 보상과 무관한 라벨이다.** 지어낸 구체적 문장이나 조작된 앱으로 얼마든지 만들 수 있으므로, 앞으로도 점수 · 경험치 · 골드 차이를 두지 않는다. 보상을 바꾸는 `VERIFIED`는 서버만 정한다.
- **자동 종료는 "다음 요청 때" 처리한다** (스케줄러 없음). 그래서 DB의 RUNNING 행이 실제로는 이미 끝난 것일 수 있다 → 합계 · 통계 쿼리는 정리를 거친 뒤 읽는다. `ended_at`은 처리한 시각이 아니라 끝나야 했던 시각.
- **날을 넘긴 타이머는 끝난 날 기록이다** (3차). 전날 밤에 한 운동 · 공부가 다음 날의 확인된 기록이 될 수 있다 (전날엔 직접 적어 최대 20, 다음 날 확인됨). 이득이 작아(×1.2 · 최대 5점, 하루 반영 3개) 막지 않는다.
- **일시정지한 타이머는 기한 없이 남을 수 있다** (경과가 늘지 않아 240분에 안 걸림). 습관마다 하나라 다른 습관을 막지 않는다. 습관이 끝나면 함께 끝난다.
- **운동 시간 판정은 타이머와 헬스 중 큰 값**이다 (더하지 않음 — 같은 운동을 둘 다로 쟀을 수 있음).
- **"운동 횟수"는 판정하지 않는다.** 시드의 "스쿼트"(운동 횟수 목표 30)는 반복 횟수인데, Health Connect의 운동 세션 수는 운동한 번 수라 뜻이 다르다.
- **자기보고 상한 20은 카테고리 차이를 만든다.** (2차 검토에서 고침) 상한이 깎는 것은 시간 · 양(`TARGET_RATIO`) 항목뿐이다 — O·X · 범위(수면)는 원래 최대 20점. 확인 수단이 없는 시간 · 양 항목(운동 횟수 · 학습량 · 물 · 끼니 · 저축액 · 자가진단)은 새로 21 ~ 25점을 못 받고, 식습관 · 수면 · 절약은 확인 계수(1.2)도 못 받는다 → 시뮬레이션에서 카테고리별로 따로 본다. 모든 사용자의 골드가 줄어드는 기획 변경이라 `economy-v1.md` · `economy.dart` · 로컬 모드도 같이 바꿔야 한다 (API 7장).
- **개인정보**: 대화는 저장하지 않지만 Gemini(Google)로 전송되고, 헬스 운동 시간은 민감정보다 → 동의 화면 · 개인정보처리방침에 둘 다 적는다 (6단계 출시 준비).
- **위기 신호는 저장하지 않는다.** 기존 `ai.chat_session.safety_flagged_at`은 이 기능에서 쓰지 않는다 (세션을 만들지 않음). 필요하면 7장에서 따로 정한다.
