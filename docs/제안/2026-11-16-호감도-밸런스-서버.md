> **11-16 검증 · 확정 (윤서 승인)** — 아래 2장의 옛 SQL은 쓰지 말고 **0장의 확정 SQL**을 쓴다.

> 검증에서 **제안이 틀렸던 점**: ① 2장 SQL의 `affection_pet_gain`이 3인데 D-79(앱 · §5)는 **1**. ② "×10이면 단계가 그대로"는 4 → 40, 7 → 70은 맞지만 **옛 3(시작값) → 30은 새 친해짐 하한(30)에 걸려 LOW → MID로 올라간다** → 옛 3만 29로 옮겨 단계를 지킨다 (B안). ③ 변환은 한 번만 해야 한다(두 번 하면 40 → 100) → 안전장치를 넣었다. ④ 시드 · 테스트 값도 같이 바뀐다(이 PR).

## 0. 확정 SQL (Supabase SQL 편집기에서 실행 → 이어서 EC2에서 서버 재시작)

실행 전에 백업: `select id, affection from monster.user_monster;` 결과를 복사해 둔다. 현재 설정 확인: `select key, value from config.balance_config where key like 'affection%' or key = 'starter_affection';`

```sql
BEGIN;

UPDATE config.balance_config SET value = '100'::jsonb,                  updated_at = now(), updated_by = 'yoonseo' WHERE key = 'affection_max';
UPDATE config.balance_config SET value = '{"MID":30,"HIGH":70}'::jsonb, updated_at = now(), updated_by = 'yoonseo' WHERE key = 'affection_tiers';
UPDATE config.balance_config SET value = '1'::jsonb,                    updated_at = now(), updated_by = 'yoonseo' WHERE key = 'affection_pet_gain';
UPDATE config.balance_config SET value = '2'::jsonb,                    updated_at = now(), updated_by = 'yoonseo' WHERE key = 'affection_play_gain';
UPDATE config.balance_config SET value = '5'::jsonb,                    updated_at = now(), updated_by = 'yoonseo' WHERE key = 'starter_affection';

-- 옛 3(시작값)만 29로: 단계가 그대로 유지됨. 이미 변환됐으면(최대값 > 10) 건너뜀 — 두 번 실행해도 안전
UPDATE monster.user_monster
   SET affection = CASE WHEN affection = 3 THEN 29 ELSE LEAST(affection * 10, 100) END
 WHERE (SELECT max(affection) FROM monster.user_monster) <= 10;

SELECT key, value FROM config.balance_config WHERE key LIKE 'affection%' OR key = 'starter_affection' ORDER BY key;
SELECT min(affection), max(affection) FROM monster.user_monster;
COMMIT;   -- 이상하면 ROLLBACK
```

- 서버는 **뜰 때 한 번** 설정을 읽는다 → COMMIT 직후 EC2에서 `sudo systemctl restart habit-monster`, 20~60초 뒤 `curl.exe -i https://api.habitmonster.me/api/v1/me/status`가 **401**이면 정상.
- 변환 결과(옛 → 새 · 단계): 0→0 · 1→10 · 2→20 · **3→29** · 4→40 · 5→50 · 6→60 · 7→70 · 8→80 · 9→90 · 10→100, 단계 LOW/MID/HIGH는 전부 그대로.
- **간식(`affection_feed_gain`)은 이 변경에 넣지 않는다.** 시드에 새 키가 생기면 `BalanceConfigTest`가 `REQUIRED`/`NOT_USED_BY_SERVER`에 넣으라고 실패하고, `affection_action.action_type`의 CHECK에 `'FEED'`(검증 파일 `verify.sql:661-666`에 시험이 이미 있음)와 API가 한 묶음이다 → 간식 API를 만들 때 따로.
- 서버 모드 하루 최대는 간식이 붙기 전까지 쓰다듬기 1 + 놀아주기 2 = 3 (D-79의 5는 간식 +2 포함) → 단짝(70)까지 약 22일(시작 5부터).
- API 명세 v6의 예시(`affectionMax: 10`, `gain 2 / affection 8` 등)는 옛 값이다 — 윤서 파일이라 안 고쳤다. 다음에 명세를 손볼 때 같이.

## (참고) 처음 제안 — 위 0장으로 대체됨

## 1. 왜
하루 +3이라 2~3일이면 단짝 · 최대. 매일 다 챙기면 친해짐 약 6일 · 단짝 약 2주 · 최대 약 3주가 되게 늦춘다.

## 2. 바꿀 것은 설정값과 기존 데이터뿐
서버는 호감도 숫자를 모두 `balance_config`에서 읽고(`BalanceConfig.affectionMax` · `affectionTier` · `affectionPetGain` · `affectionPlayGain` · `starterAffection`), `monster.user_monster.affection`은 `CHECK (affection >= 0)`뿐이다. → **서버 코드 · 스키마 · API 명세는 그대로.**

| 키 | 지금 | 제안 |
| --- | --- | --- |
| `affection_max` | 10 | **100** |
| `affection_tiers` | `{"MID":4,"HIGH":7}` | **`{"MID":30,"HIGH":70}`** |
| `affection_pet_gain` | 2 | **3** |
| `affection_play_gain` | 1 | **2** |
| `starter_affection` | 3 | **5** |

```sql
UPDATE config.balance_config SET value = '100'::jsonb             WHERE key = 'affection_max';
UPDATE config.balance_config SET value = '{"MID":30,"HIGH":70}'::jsonb WHERE key = 'affection_tiers';
UPDATE config.balance_config SET value = '3'::jsonb               WHERE key = 'affection_pet_gain';
UPDATE config.balance_config SET value = '2'::jsonb               WHERE key = 'affection_play_gain';
UPDATE config.balance_config SET value = '5'::jsonb               WHERE key = 'starter_affection';

-- 기존 호감도 옮기기 (한 번만): 단계가 그대로 유지된다 (4 → 40 친해짐, 7 → 70 단짝)
UPDATE monster.user_monster SET affection = LEAST(affection * 10, 100);
```
> 테이블은 `config.balance_config`(`value`는 JSONB, schema.sql 792행). 시드(`seed.sql` 399~403행)도 같은 값으로.

- 서버는 **뜰 때 한 번** 설정을 읽어 둔다(`BalanceConfig`) → **값을 바꾼 뒤 서버 재시작 필요**.
- `affection_action`에 이미 남은 gain(2 · 1)은 기록이라 그대로 둬도 된다.

## 3. 앱과 같이 내보내야 함
앱이 0~100 기준(하트 한 칸 = 20, 단계 30/70)으로 바뀐다. 서버가 0~10을 주면 하트가 거의 비고 모두 "서먹한 사이"가 된다. 서버 값 변경 · 앱 `dev` 머지를 같은 때 한다.
